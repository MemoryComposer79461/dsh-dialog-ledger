# 04 · 回滚方式 · `v0.9.3`（lite 线）

> 原则：**回滚的是代码，不是账。** 账本 `ledger/*.jsonl` 只追加、不回改；本版**不迁移旧库、不改台账行格式（`v:3`）、不改数据总库布局、不新增配置键**——所以回滚只需要换代码，账库一个字节都不用动。
> 本文件给出三个回滚点、三种回滚动作、**数据回滚口径**、回滚后必核项与演练步骤；**演练结果已由 lead 实跑并填在文末**。
> 依据：`VERSION.json`（`baselineTag=lite-v0.9.3-snap`、`rollback=git reset --hard lite-v0.9.3-snap`）；tag/提交/快照数字均为本文件写作时**现场实测**（`git rev-parse` / `git ls-tree -r -l` / `snapshots\v0.9.3-re1\snapshot.json`）。

## 一、回滚点（tag / 提交 / 快照，现场实测）

| 目标 | tag | tag 指向提交 | `VERSION.json` / 台账记录 | 目录快照（`_工作\snapshots\`） | 适用场景 |
|---|---|---|---|---|---|
| v0.9.1 正式版 | `lite-v0.9.1` | `f932108` | 台账第 5 行 | **无**（旧机快照未带过来） | 退回 0.9.1（账库口径同 0.9.1；本版新增的 `.tick-metrics.jsonl` 它不认识，忽略） |
| v0.9.2 正式版 | `lite-v0.9.2` | `71f259c` | `VERSION.json.version=0.9.2`；台账第 8 行 | **无**（旧机快照未带过来） | 退回上一个正式版（结构收敛版；**E3 大语料缺陷会回来**） |
| v0.9.3-snap | `lite-v0.9.3-snap` | `a7bd76e` | 代码提交 `347d439`；台账第 9 行 | **无**（旧机快照未带过来） | **退回本版开工前**（本版 `VERSION.json.rollback` 指定的默认目标） |
| **v0.9.3-re1（本版构建依据）** | `lite-v0.9.3-re1` | `6082b9c` | 代码提交 `f70a871`；台账第 10 行 | `v0.9.3-re1\tree`（**456 文件 / 6,868,175 B**，`snapshot.json` 实测） | 本版；回滚后复位回这里 |
| **本版正式 tag** | `lite-v0.9.3`（**待 lead 打**） | — | `VERSION.json.version=0.9.3`；`type=re1` 升正式；台账第 11 行待补 | 同 re1 | 正式版发布点；打 tag + 追加台账后本版才算发布 |

> 读法：tag 指向的是"记录提交"（把代码提交哈希写进 `VERSION.json`/`版本台账.md` 的那次），**tag 提交 ≠ 代码提交**：
> - `lite-v0.9.3-snap` = `a7bd76e`，其代码提交是 `347d439`；
> - `lite-v0.9.3-re1` = `6082b9c`，其代码提交是 `f70a871`。
> 两者树内容只差元数据（`VERSION.json`、`版本台账.md` 的哈希/行）。"看代码"用代码提交；"复位到某版"用 tag。
> 当前 HEAD = `6082b9c`（`6082b9c42c97fae7969d29312ffdfc73802252ca`），`git status --short` 为空（工作树干净；本版交付五件 `交付-v0.9.3/` 是**未跟踪**新增目录）。
> **旧机崩溃的后果（如实写）**：`_工作\snapshots\` 下现在**只剩 `v0.9.3-re1` 一份**目录快照（旧机上的 snap/re1 快照全部丢失）；也没有 restore 脚本（旧机 `snapshot.ps1` 丢失，新机只重建了 `_工作\tools\snapshot.mjs` 的"建快照"能力）。所以**动作③只能恢复 re1**，且是手工镜像（见 §二③）。

## 二、三种回滚动作

先设两个路径变量（下同）：

```powershell
$git  = '<build-host>\_工作\tools\MinGit\cmd\git.exe'
$repo = '<build-host>\_工作\lite'
```

### ① `git reset --hard`：整树退回上一版（默认动作）

```powershell
& $git -C $repo rev-parse HEAD                  # 先记下当前 HEAD（本版应为 6082b9c…）
& $git -C $repo status --short                  # 先确认工作区干净（本版：空）
& $git -C $repo reset --hard lite-v0.9.3-snap   # 退回开工前（$VERSION.json.rollback）
& $git -C $repo rev-parse HEAD                  # 期望 a7bd76e…
```

- 期望：HEAD 从 `6082b9c` 变为 `a7bd76e`；`VERSION.json.type` 变 `snap`；`cordis.patch.yml` 的 `scanBudgetMs` 回到 **30000**（snap 已是 30000，不是回 3000）；`git status --short` 只剩未跟踪的 `交付-v0.9.3/`（未跟踪文件不会被 `--hard` 删除）。
- 代价：丢弃**已跟踪文件**的未提交修改；不会删除未跟踪文件（`交付-v0.9.1/`、`交付-v0.9.2/` 是已跟踪目录，`--hard` 会把它们恢复成目标版本中的样子；`交付-v0.9.3/` 不在任何旧 tag 里，属未跟踪，保留）。
- 本仓库 `core.autocrlf=false`（0.9.1 实测；本版未改），复位**不做换行转换**，工作区字节与提交一致。
- 退回 0.9.2 正式版：`& $git -C $repo reset --hard lite-v0.9.2`（HEAD 变 `71f259c`；`VERSION.json.version=0.9.2`；**`cordis.patch.yml` 回到 `scanBudgetMs: 3000`**；测试基线回到 504/460/44；内核基线文件仍在，默认 PASS）。
- 退回 0.9.1 正式版：`& $git -C $repo reset --hard lite-v0.9.1`（HEAD 变 `f932108`；测试基线回到 **504 / 469 / 35**；内核检查回到"对 v1.0-lite 基线不存在、对 0.5.0 红恰 2 changed"的旧口径）。
- 复位回本版：`& $git -C $repo reset --hard lite-v0.9.3-re1`（HEAD 回 `6082b9c`）。

### ② `git checkout <tag> -- .`：只取文件，不动分支指针

```powershell
& $git -C $repo checkout lite-v0.9.3-snap -- .
# 或只退单个文件（例：只把三处读放大修复退回去，保留 .tick-metrics 写入）
& $git -C $repo checkout lite-v0.9.3-snap -- lib/weekly.js lib/original.js lib/reconcile.js
```

- 期望：工作区文件变成目标 tag 内容，HEAD 不变，`git status` 显示一堆"已修改"——这是**故意**的，用于"只拿旧文件比对/临时跑一下/只退一个模块"。
- 注意：`checkout -- .` **不会删除**目标 tag 里不存在的文件（例如 `lib/tickmetrics.js`、`docs/工具-日检.mjs` 在 `lite-v0.9.2` 里不存在，会留在盘上；**但此时 `index.js` 已退回旧版，不会 import 它们**，属"死文件"，不影响运行；要干净复原请用 ①）。
- 想恢复成 HEAD：`& $git -C $repo checkout HEAD -- .`。

### ③ 目录快照恢复（不走 git；最接近"逐字节复原"）

**前提（重要）**：快照树里**没有 `.git`**（`snapshot.mjs` 的 `copyDir` 跳过 `.git`），而 `snapshots\v0.9.3-re1\tree` 是**整仓 456 文件**（含 `交付-v0.9.1/`、`交付-v0.9.2/`、`MANIFEST.sha256`）。所以：

**不要**直接把快照 `robocopy /MIR` 到 `_工作\lite` 根目录——`/MIR` 会**删掉 `.git`**（仓库历史和 tag 全没），也会删掉本版 `交付-v0.9.3/`。正确做法二选一：

```powershell
# 方案 A（推荐）：在副本目录里恢复与校验，不碰工作仓库
$snap = '<build-host>\_工作\snapshots\v0.9.3-re1\tree'
$dst  = '<build-host>\_工作\回滚演练B\v0.9.3-re1'   # 或任意空目录
robocopy $snap $dst /MIR /NFL /NDL /NJH /NJS

# 方案 B：原地恢复（先移出 .git 与 交付-v0.9.3，再镜像，最后放回）
$lite = '<build-host>\_工作\lite'
Move-Item "$lite\.git"          '<build-host>\_工作\_tmp-git-暂存' -Force
Move-Item "$lite\交付-v0.9.3"   '<build-host>\_工作\_tmp-交付v093-暂存' -Force
robocopy $snap $lite /MIR /NFL /NDL /NJH /NJS
Move-Item '<build-host>\_工作\_tmp-git-暂存' "$lite\.git" -Force
Move-Item '<build-host>\_工作\_tmp-交付v093-暂存' "$lite\交付-v0.9.3" -Force
```

- 期望：恢复后按 `snapshots\v0.9.3-re1\snapshot.json` 核对 = **456 文件 / 6,868,175 B**；逐文件 sha256 与 `snapshots\v0.9.3-re1\manifest.sha256`（456 行）比对 **missing=0 / changed=0 / extra=0**（方案 A）；方案 B 放回交付目录后 `extra=5`（交付五件，属预期）。
- 注意：快照是 **re1 整树**（含 `MANIFEST.sha256` 的代码树版本，455 行）；恢复后 `git status` 会全量"已修改"（工作区与 HEAD 不一致属预期）——**恢复后不要直接 commit**，先 `git reset --hard lite-v0.9.3-re1` 对齐，或只在副本目录里用快照。
- **没有 snap / 0.9.2 的目录快照**：要那种"逐字节复原"，只能用 `git reset --hard <tag>`（动作①）代替。

## 三、数据回滚口径（★ 本版重点）

### 3.1 一句话

**账库只追加、本版无数据迁移 → 代码回滚不用动账；本版新增的 `.tick-metrics.jsonl` 可留可删。**

### 3.2 逐对象口径

| 对象 | 回滚时怎么处理 | 为什么 |
|---|---|---|
| `ledger/YYYY-MM-DD.jsonl`（台账） | **不动** | append-only；按设计不允许"撤回一行"，只能补记/更正留痕 |
| `YYYY年MM月/…完整原文.md`、`原始事件.json` | **不动** | 本版不销毁原文（清理仍冻结），回滚不会产生"文件没了"的问题 |
| 周记账 `xlsx`（草稿/封板） | **不动** | 封板后字节不变，回滚代码不会重写 |
| `ledger/.seal-journal.jsonl` | **不动** | 封板事实由摄入路径写，回滚不重写（S-1 只写"封板事实"） |
| `ledger/.state.json` / `.pending.jsonl` | **不动** | 游标/进行中轮次是运行状态，非证据；旧代码能读（字段只加不改；本版**没有新增 state 键**） |
| `ledger/.run-report-YYYYMMDD.json` | **不动** | 报告形状未变（本版只新增 `.tick-metrics.jsonl`，没改 run-report 键） |
| **`ledger/.tick-metrics.jsonl`（本版新增）** | **可留可删** | ① 只有本版会写它，旧代码（0.9.2/0.9.1）**不读**；② `.` 开头 → 台账枚举/指纹/行数都不把它当账行；③ 它是度量旁证，不是账务事实——留着便于比对，删掉不影响任何账务。**删不删都不需要同步改账库** |
| `<root>/报告/日检-YYYYMMDD-NN.json`（本版新增能力，若跑过） | **可留可删** | 只有跑过 `docs\工具-日检.mjs` 才有；不参与记账。注意 `报告/` 是**新的一级目录**，`lib/layout.js` 会把它记进 `unknown[]`（0.9.1 起就如此）——回滚前若跑过日检/doctor，这是预期现象，不是布局被破坏 |
| `交付-v0.9.3/`（本包 5 个 md） | 动作③（/MIR）前先移出 | 不在快照里，/MIR 会删 |
| 配置（`cordis.patch.yml`） | 用整树回滚（动作①）一并回退 | 本版改过 `scanBudgetMs` 默认值；若只回滚代码不回滚配置，会出现"0.9.2 代码 + 30000 配置"的混搭（不报错，但口径不一致） |
| 公共库外锚 / 收据 | **不涉及** | 本版未启用、未写；收据能力按 S-1 已降级为日结摘要 |

### 3.3 回滚 = 换代码，四条硬理由

1. **台账行格式未变**：仍是 `{"v":3, code, ts, sid, turn, seq, status, turnState, src, doc, …}`；本版**没有动 `lib/ledger.js` 的行结构**（K-2 只透传读取参数）。
2. **配置 21 键未变**：`cordis.patch.yml` 键集合仍是 21 个、其余 20 键逐键同值；只有 `scanBudgetMs` 的默认值变（3000↔30000）。
3. **数据总库布局未变**：`lib/layout.js` 本版未改；新增的 `.tick-metrics.jsonl` 在 `ledger/` 下且 `.` 开头，不改变布局判定。
4. **本版不迁移旧库**：`legacy-marks` 冻结、`reconcile` 不读基线标记 → 本版没有"升级动作"要撤销；反过来，**本版也没有提供旧库升级路径**（见 03 §六）。

### 3.4 ★ 数据回滚的三个"必须知道"

1. **代码回滚 ≠ 数据补齐**：本版已在 E3 大语料上入账 **1,338 行**；回滚到 `lite-v0.9.3-snap` 或 `lite-v0.9.2` 后，**这 1,338 行不会回退**（台账只追加），但**E3 的"停滞 + 每轮重复读"缺陷会回来**——旧代码按 `.state.json` 游标继续，大语料会再次停在巨帧起点。正确做法：回滚只用于"回到能跑的版本"，大语料要么等本版（或更新版）修复后重跑，要么接受停滞。
2. **`.tick-metrics.jsonl` 会让"目录全量比对"出现差异**：回滚到 0.9.2 后该文件不再增长，但**已写的行仍在**；如果有人拿"回滚前/后目录 sha 集合"做审计，需把该文件排除或明确"可留可删"（本文件即口径）。
3. **退到 v0.9.0 基座的"读语义差异"仍在**（沿 0.9.2 04 §3.3）：本版 `ledger/.seal-journal.jsonl` 按 S-1 只写"封板事实"（`prevSealSha256` 恒 `''`），0.9.0 基座代码读本版写过的库会把缺链行按"链断/坏行"处理 → 门可能降级。**默认回滚目标 `lite-v0.9.3-snap`/`lite-v0.9.2`/`lite-v0.9.1` 都是同一口径，没有这个问题；退基座只用于"整包回看/比对"。**

## 四、回滚后必须核的事

| # | 检查 | 命令 | 期望 |
|---:|---|---|---|
| 1 | 版本对不对 | `& $git -C $repo rev-parse HEAD`；读 `VERSION.json` 的 `version/type/commit` | HEAD = 目标 tag 指向的提交（snap `a7bd76e` / re1 `6082b9c` / 0.9.2 `71f259c`）；`type` 与目标一致（`snap` / `re1`） |
| 2 | 工作区干不干净 | `& $git -C $repo status --short` | 只有 `?? 交付-v0.9.3/`（未跟踪）；其余为空 |
| 3 | 核心边界没被破 | `node tools\core-boundary.mjs` | **re1 / snap：exit 0，`[PASS] 0 violation`，`core files 22`，index→tools 3 条**；0.9.2：exit 0、`core files 21`、index→tools 3 条 |
| 4 | 内核基线对不对 | `node docs\验收-v0.5\工具-内核边界检查.mjs` | **re1 / snap：`[PASS] exit 0`**（v1.0-lite 基线；re1 另提示受控变更 3 个）；0.9.2：`[PASS] exit 0`（同基线）；0.9.1：exit 1（对 0.5.0 红恰 2 changed，且无 v1.0-lite 基线） |
| 5 | 测试基线回到该版 | `node docs\跑测试.mjs` | **re1 / snap / 0.9.2：504 / 460 / 44**（44 红均为已登记退役/日期，见 02 §五）；0.9.1：504 / 469 / 35（约 39 s；可用内存 <900 MB 时会被护栏 exit 3 拒绝启动，是环境不是失败） |
| 6 | 判据工具在不在 | `Test-Path docs\判据-0.9.1.mjs`；`Test-Path docs\判据-0.9.2-doctor.mjs`；`Test-Path docs\工具-日检.mjs` | re1：三个都在；snap：判据·doctor 在、**日检在**（snap 已含）；0.9.2：判据·doctor 在、日检**不在** |
| 7 | 账库一个字节没动 | 回滚前后各算一次账库文件 sha256 集合（`Get-FileHash -Recurse`） | 集合完全相同（`.tick-metrics.jsonl` 若不删，回滚后不再增长但内容不变）；台账行数与回滚前一致（**不会因回滚变多/变少**） |
| 8 | 配置口径对不对 | `Select-String -Path cordis.patch.yml -Pattern 'scanBudgetMs'` | re1 / snap：`scanBudgetMs: 30000`；0.9.2：`scanBudgetMs: 3000`；**代码与配置必须同版**（动作① 自动保证） |

> 内存护栏：`node docs\跑测试.mjs` 在可用内存 <900 MB 时**拒绝启动（exit 3）**，不是测试失败；回滚后若机器忙，先释放内存再跑。

## 五、回滚演练（步骤 + 预期；实际结果由 lead 补）

> 演练纪律：在 `_工作\lite` 内做（动作③ 用副本目录）；演练前先 `git status` 确认没有未提交的已跟踪改动；演练只碰代码，不碰账库（`_工作\c01-lab` 只读跑判据，不写）。
> **说明**：`_工作\snapshots\` 只有 `v0.9.3-re1` 一份快照，所以演练 B 的"恢复 snap 快照"一步**没有素材**——B 只能对 re1 快照做"恢复 + 逐字节校验"（这与 0.9.2 的 B 演练范围不同，如实记）。

### 5.1 演练 A · git 退回开工前再复位（默认路径）

```powershell
$git  = '<build-host>\_工作\tools\MinGit\cmd\git.exe'
$repo = '<build-host>\_工作\lite'

& $git -C $repo rev-parse HEAD                     # A1 记录演练前 HEAD
& $git -C $repo reset --hard lite-v0.9.3-snap        # A2 退回本版开工前
& $git -C $repo rev-parse HEAD                     # A3
node tools\core-boundary.mjs                       # A4
node docs\跑测试.mjs                               # A5（约 39 s）
& $git -C $repo reset --hard lite-v0.9.3-re1        # A6 复位回本版
& $git -C $repo rev-parse HEAD                     # A7
node docs\判据-0.9.1.mjs --lab=<build-host>\_工作\c01-lab   # A8 回到 18 绿
```

| 步 | 预期（可逐条对照） |
|---|---|
| A1 | `6082b9c…`（re1 记录提交） |
| A2 | `git reset` 成功，无冲突；`VERSION.json.type` 变 `snap`；`cordis.patch.yml` 仍 30000 |
| A3 | `a7bd76e…`（snap 记录提交） |
| A4 | `exit 0`，`[PASS] 0 violation`，core files **22**，index→tools **3 条** |
| A5 | **504 例 / 460 通 / 44 红 / exit 1**（与 snap 台账一致） |
| A6 | 成功；`VERSION.json.type` 回 `re1` |
| A7 | `6082b9c…`（与 A1 相同） |
| A8 | **GREEN=18 / RED=0 / NA=0 / SKIP=0**（与 02 §二 一致） |

### 5.2 演练 B · 目录快照恢复（逐字节复原路径）

```powershell
# B1 确认素材：snapshots\v0.9.3-re1\snapshot.json（456 文件 / 6,868,175 B）
# B2 方案 A：robocopy snapshots\v0.9.3-re1\tree → 副本目录（不碰 .git、不碰交付目录）
# B3 逐文件 sha256 与 snapshots\v0.9.3-re1\manifest.sha256 比对：missing=0 changed=0 extra=0
# B4 方案 B（可选）：原地恢复 = 先移出 .git 与 交付-v0.9.3 → /MIR → 放回 → git reset --hard 对齐
```
