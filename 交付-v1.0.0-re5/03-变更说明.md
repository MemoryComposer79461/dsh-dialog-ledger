## 二、改动 1 · P-01：运行度量分档（`tools/doctor.mjs`）

**问题**（2026-11-22 七天运行报告 §六 / 08 问题清单 P-01）

```
ledger\.tick-metrics.jsonl：8,171 行 / 18.10 MB / ≈2.32 KB 每行 / 按设计每 tick 追加、无界
doctor 的 4 MiB 单文件哨兵是为"账务数据文件"设的，却套到了这个运行度量文件上
→ 真实运行约 1.3 天必红；7/0/3 门槛永远达不到；容量告警失去信号价值
而 tools/backup.mjs 又把同一文件定义为「运行度量，非账务事实」默认不备份 —— 口径自相矛盾
```

**改法**（只动 `tools/doctor.mjs`，不动 `judge`、不动 `index.js`/`lib/`）

```js
// 新增：运行度量档阈值与判定
const MAX_METRICS_FILE_BYTES = 64 * 1024 * 1024;
function isRuntimeMetricsPath(relPath) {
  return /(^|\/)ledger\/\.tick-metrics[^/]*\.jsonl$/.test(String(relPath).replace(/\\/g, '/'));
}
// 账务数据文件：仍 4 MiB 哨兵（且排除运行度量）
const bigNonXlsx = sorted.filter((f) => f.size > MAX_SINGLE_FILE_BYTES
  && !/\.xlsx$/i.test(f.path) && !isMetrics(f));
// 运行度量：>4 MiB 属设计内（只报告），>64 MiB 判红（不静默）
const bigMetrics = sorted.filter((f) => isMetrics(f) && f.size > MAX_METRICS_FILE_BYTES);
```

**为什么是 64 MiB**：按 1,440 tick/天 × ≈2.32 KB ≈ 3.2 MB/天，64 MiB ≈ 20 天；既覆盖"几十天真实长跑"，又保留一个**会报警**的上界（不把哨兵关掉）。轮转/硬上限排 1.1（见 `05-已知未覆盖项.md` 第 1 条）。

**影响面**：只影响 `doctor` 的 storage-health 结论；**不影响**台账/对账/封板/写入路径（KERNEL 六文件逐字节未变）。

**验证（本轮实跑，三向 + 一边界）**

| 场景 | 期望 | 实测 |
|---|---|---|
| 20 MB `.tick-metrics.jsonl`（= 7 天实跑等量） | ok | ✅ ok |
| 20 MB 度量 + 5 MB 账务文件 | red（账务哨兵仍有效） | ✅ red |
| 70 MB `.tick-metrics.jsonl` | red（度量档仍封顶） | ✅ red |
| 20 MB `.tick-metrics-202611.jsonl`（轮转名） | ok | ✅ ok |

**C44 未回归**：C44 注入的故障是普通 5 MB 文件（`临时大文件.bin`）与 1.2 MB `.pending.jsonl`，仍按 4 MiB / 1 MiB 判红 → 45 条判据里 C44 **45/45 仍绿**。
