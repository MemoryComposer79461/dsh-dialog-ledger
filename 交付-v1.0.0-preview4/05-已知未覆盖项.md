## §K · v1.0.0-preview4 新增：两条「硬边界」的明确披露

> 依据：机主 2026-11-15 指令（多写者硬断言 / F-3 采方案 B）。以下两条**不是缺陷待办**，是**明确的支持边界**；
> 都已落地为可执行的硬断言，并有回归锁（见 `docs/自测-守卫.mjs`、`docs/自测-F3帧契约硬断言.mjs`）。

### K-1 多写者场景：**不支持；启动即拒绝**

- **口径**：同一个账库根（`config.root`）**只允许一个写者**（一个 DSH 实例 / 一个插件挂载）。
- **实现**：锁的创建是 OS 级原子操作（`lib/lock.js`：`fs.openSync(<root>/ledger/.lock, 'wx')` = `O_CREAT|O_EXCL`，
  创建失败即退，**不是**"先检查后启动"；也不存在两个进程同时通过检查的窗口）。
- **被挡住时的行为（硬断言，不许"警告后继续"）**：
  1. 打 **ERROR**「拒绝启动：账库已被另一个写者持有」；
  2. **停止正常 tick 节奏**，改为每 30 秒重试一次（这同时是僵死锁接管所需的"两轮确认"）；
  3. 取到锁后自动恢复正常节奏；运行中若发现锁被接管（`handle.lost`）→ **立即停手**（中止本轮、不再写任何批）+ ERROR。
- **不支持的理由**：多写者不是需求，是事故（两实例同时写 = 账只追加、无法证明哪行是真的）。
  代码级 fencing/CAS 需要改 KERNEL，**排 1.1 评估**；在此之前以"启动即拒绝"作为硬边界。
- **回归锁**：`docs/自测-守卫.mjs` 的「③·日志 / ③ 双实例」用例断言 `lockBlocked=true` + ERROR「拒绝启动」+ 账本零写入。

### K-2 「帧 = 整行」契约：写死为假设；违约即**停手报警**

- **契约**：DSH 会话写入器保证每个 zstd 帧以**完整 JSONL 行**结束（帧边界 = 行边界）。
- **硬断言**：读会话时启用 `assertLineBoundary`；若某帧解压文本非空、不以 `\n` 结尾、**且后面还有帧**
  → 判定契约被破坏 → **立即停手**：该帧记 `failedRanges(reason=contract-violation)`、`.lost` 留痕、
  游标 **不许越过该帧起点**、打 ERROR「帧=整行契约被破坏（硬断言停手）」；**不看后面的帧、不静默丢跨帧残片**。
- **边界**：**最后一帧**不以换行结尾 = 合法的"截断尾"（进程被杀/正在写），不在此列。
- **不做跨帧 pending 缓冲的理由**：那要改 KERNEL 读取算法（签字 + 全量回归 + K-16 是前车之鉴）；
  多写者/半行属于"写入方违约"的事故，用硬断言暴露比自愈更符合"零静默"。
- **将来**：若真实出现写入方违约场景，再评估改 KERNEL 做跨帧拼接（登记为 1.1 观察项）。
- **回归锁**：`docs/自测-F3帧契约硬断言.mjs`（A：违约必须停手+ERROR+.lost 留痕；B：截断尾不许误报）。
