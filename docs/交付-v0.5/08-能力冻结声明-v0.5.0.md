# 08 · 前五条能力冻结声明（v0.5.0 基线）

> **性质：口径级决定。** 机主 2026-11-09 明确：V0.5 确定整个插件的运作机制，
> **《日常会话记录插件 架构设想.docx》前五条能力以后不可撼动**。
> 本文件把"不可撼动"落成**可核查条款**，而不是一句口头承诺。
> 任何后续版本违反本文件 §三 的"冻结项"，视为**破坏基线**，不得发布。

---

## 一、机主原话（归档）

> 作为会计行业的用户，我对这个系统的定位是"银行日记账"，"交接表"就是表头目录，
> "完整原文"就是初始凭证，"周记账"就是记账凭证，那么原始凭证可以处理，
> 但处理时当然要留下清册档案，这就是整个插件的具体架构。
>
> 五个模块：**数据库组建 → 交接表生成 → 完整原文生成 → 周记账生成 → 数据管理**。

**映射到会计语义（不可倒置或合并）**：

| 能力 | 会计角色 | 事实地位 |
|---|---|---|
| 完整原文 | 原始凭证 | **事实源**（可回溯到会话/轮/字节区间） |
| 台账 `ledger/*.jsonl` | 银行日记账 | **事实源**（v0.5 新增，属实现层，见 §四） |
| 周记账 | 记账凭证 | **派生视图**（给用户读，可由台账重算） |
| 交接表 | 表头目录 | 派生视图（会话级索引 + 上下文备份） |
| 清册 | 销毁清册 | 删除行为的唯一凭据 |

## 二、冻结的五个能力（逐条，含"必须成立"的可判定点）

### 能力 1 · 数据库组建
- **顺序不可逆**：先有数据库，才有其它一切；库不成 → 插件必须停用，不得"带病记账"。
- **三级结构不可变**：数据总库 → 各月份文件夹 → `xx月总"完整原文"文件夹`。
- **自动补建**：每月 / 每周 / 每个新 session 缺失的目录会被自动补建（含热修复）。
- 判定点：库缺失时 `runOnce` 拒绝工作；三级目录缺失后一轮内自动恢复。

### 能力 2 · 交接表生成
- 只对**未归档**的 session 生成；每个 session **仅一次**，生成后标记「已生成」，之后不再生成新表。
- **交接主表 + 交接附表**成对存在；附表承载该会话的上下文备份。
- 交接表一律在**第一级**文件夹。
- 判定点：同 session 重复扫描不产生第二份；主/附表 hash 可复核（CH-13）。

### 能力 3 · 完整原文生成
- 位置**只在第三级**文件夹；**每完成一轮 Turn** 生成一份。
- 必须经编码器取得**编号前缀**，落盘名为 `编号 完整原文.md`；同月归入当月总文件夹。
- 24 小时内遗漏的必须补生成，且**文件名带缺省标记**（原文口径为"（遗漏）"）。
- 判定点：每轮一文件、文件名带编号、附件/双哈希可复核（INV-21…24、CH-01…06）。

### 能力 4 · 周记账生成
- 位置**只在第二级**文件夹；文件名带**前 12 位编码**前缀。
- 内容按对应"编号＋完整原文"填写（v0.5 起由台账重算，见 §四之 2）。
- 前三天遗漏必须**补记**，并按正序时序排序，补记行在编码栏有可识别标记。
- 判定点：周记账可由台账独立重算得到同值（M3 反证）；>120 行走补记册（INV-15…17）。

### 能力 5 · 数据管理（清理）
- 可按月份 / 数量 / session 清理**完整原文**；清理前必须**显式确认**。
- 清理与「完整原文清理报告」**同时进行**；进度可视。
- 能删的删、不能删的跳过，并**在报告中写明原因**。
- 判定点：默认零删除；清册 17 键 + S1–S8 + 复核行（CL-01…32）。

## 三、冻结项 vs 可演进项

**冻结（改 = 破坏基线）**
1. 五个能力的**存在性与先后依赖**（1→2→3→4，5 依赖 3 的产物）。
2. 三级目录结构与各能力的**落盘层级**。
3. 会计语义映射（原文=原始凭证、周记账=记账凭证、清册=销毁凭据）。
4. 每轮一原文、每 session 一交接表、周记账含前 12 位编码。
5. 清理必须留清册、必须显式确认、必须默认不删。

**可演进（不视为破坏）**
- 实现语言/模块划分/性能优化；台账 jsonl、收据锚、封板 canonical 等**新增**机制。
- 报告字段、错误码、CLI/工具形态。
- UI 层（v0.6 才做，见 §五）。
- 补记的具体承载方式（见 §四之 3）。

## 四、v0.5.0 已存在的三处理解差异（需机主确认"能力等价"）

> 这三处是 v0.5 与 docx 字面不同、但能力未减的地方。列出来是为了**不偷偷改**。

1. **建库方式**：docx 要求"首次使用弹窗智能选择（默认）"；v0.5.0 用配置项 + 明确的"未建库则停用"行为，**弹窗属 UI 层，延至 v0.6**。
2. **周记账的数据来源**：docx 写"内容通过对应完整原文 .md 填写"；v0.5.0 改为**由台账重算**（两者同一 32 位编码，可互相回指）。机主已确认此设计"相当不错"。
3. **补记的承载**：docx 规定补记行编码后缀 `-B`；v0.5.0 改为**独立的补记册**（`overflow-seal`）承载溢出补记，正册仍 120 行上限。
   —— **机主 2026-11-09 裁定：接受。** 原话要点："后缀加 -B 只是比较初期的想法，工程学重要的是实现，
   以更方便、更稳定的形式实现，比天马行空拆台子来得好。" 因此本项归入 §三"可演进项"，`-B` 不再是冻结项。

## 四之二、机主 2026-11-09 的补充裁定（三条）

1. **数据库组建属于外围**：以后的改动**不接触内核**，或只改"编码逻辑"与"周记账内容"；其余改动**只在数据库层面**发生（例如移动数据库后的重新检测与定位）。因此 **v0.6 属于外层更新**。
2. **会计学与工程学是两个概念**：用会计逻辑创作插件，**具体实现更重要**；不因字面教条而牺牲实现的稳定性。
3. **32 位编码的冗余是可调的**：Session ID 的 12 位可缩到 8 位、序列号可缩短，代差（防小概率事件）才是关键；"多加 2 位在成熟系统看来大可不必"。
   —— 这是**方向**，不是本版动作。缩位须先做碰撞概率分析并走升版流程（见 §六之 3）。

## 五、后续版本的硬约束

1. 任何改动若触及 §三"冻结项"，必须：**升版 + 出差异清单 + 机主签字**，否则不得发布。
2. 新版本必须能回答：五个能力各自**在哪里实现、用什么判据验收、证据文件是什么**（对应 §二 判定点）。
3. UI（docx §6）属 v0.6 范围；它只做**呈现与入口**，不得改变五个能力的落盘语义。
4. 每一版交付包必须包含本文件的**最新版本**，并在发布页登记"冻结基线未变"的核对结果。

## 六、内核边界（可自动检查）

机主裁定"不接触内核"之后，必须回答一个工程问题：**哪些文件算内核？** 本文件按"是否决定账对不对"划三层：

| 层 | 内容 | 规则 |
|---|---|---|
| **KERNEL（禁改）** | `lib/ledger.js`（台账唯一写盘/查重/撕裂尾巴自愈）、`lib/frames.js`（帧边界与坏帧）、`lib/sealjournal.js`（封板链 + canonical v8）、`lib/pending.js`（未闭合轮）、`lib/lock.js`（单实例锁与接管）、`lib/week.js`（周锚） | 改动 = **破坏冻结基线**，必须升版 + 机主签字 |
| **CONTROLLED（受控可改）** | `lib/encoder.js`（编码逻辑）、`lib/weekly.js`（周记账内容）、`lib/xlsx.js`（产物格式底座）、`lib/{handover,original,cleanup,receipt,reconcile,selfheal,backfill,checkup,legacy,sealcross}.js`、`index.js` | 允许变，但**必须五门全绿**并在本版差异清单登记 |
| **自由（外层）** | 数据库定位/迁移/重检测、配置、UI、工具、报告呈现、文档、测试 | v0.6 的主战场，可自由演进 |

**工具**：`docs/验收-v0.5/工具-内核边界检查.mjs`
- 基线：`docs/内核基线/内核基线-0.5.0.sha256`（从 0.5.0 冻结包现场生成，6 KERNEL / 14 CONTROLLED）
- 用法：`node docs/验收-v0.5/工具-内核边界检查.mjs`（退出码 0 = 内核逐字节未变；1 = 内核被改）
- 每次发版前必须跑一次，并把结果写进发布页。

**已知限制（如实写）**：`index.js` 同时装内核编排与外层调度，**无法按文件切分**，故整体归 CONTROLLED；
其内核语义由 INV/CH/REC/CL 判据守，不由哈希守。

### 六之 3 · 编码冗余的调整规则（32 位编码）

- **现在**：保留 32 位（`YYYYMMDD-SSSSSSSSSSSS-T-NNNNNNNN`）的冗余，作为防御性设计；**不加长**。
- **若要缩短**（如 Session ID 12→8 位、序列号缩短）：
  1. 先做**碰撞概率分析**（在预期会话量/年下，编码冲突的期望次数）；
  2. 必须有**代差**（相邻编码跨代隔离，避免同段内密集碰撞）；
  3. 走**升版 + 差异清单**，并证明旧账库仍可读（向后兼容）；
  4. 五门全绿后方可发布。
- 判定点：编码唯一性由 `INV-15/16/17`（封板 hash 互异、120+5 闭合）与状态查重守住。
