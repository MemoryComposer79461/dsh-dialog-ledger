## 探针 1 · 同字节数重写：头部指纹窗口之外的内容变化会被漏记

**要复现的边界**：`index.js` 判定"源文件没变"用的是 `sameSize && sameIdentity`，其中 `sameIdentity = sha256(文件头 headFingerprintBytes 字节)`。默认 `headFingerprintBytes = 4096`（现场取 `index.js::__test__.DEFAULTS.headFingerprintBytes = 4096`）。因此：
- 若重写发生在**前 4096 字节之内** → 指纹变 → 走全量重读（有对照，见下）；
- 若重写发生在**前 4096 字节之外**、且**总字节数不变** → 指纹与大小都不变 → 走 `unchanged` 快路径 → **新内容永远不进账**。

**构造（现场造数）**
```
临时 lab；会话文件 = 前缀帧（session 头帧 + turn1 帧，turn1 内含 6000 字符随机填充，前缀 4856 B > 4096）
               + 尾帧（turn2：user/message 文本内含标记 mA）
V1 = prefixA + tailA        ← run1 → turn1/turn2 入账
V2 = prefixA + tailB        ← 总字节数相同、前 4096 字节完全相同、整文件 sha256 不同
V3 = prefixB + tailA        ← 对照组：总字节数相同，但差异落在前 4096 字节内
```
**命令**
```powershell
$node = '<test-dir>\resources\runtime\primary-runtime\dependencies\node\bin\node.exe'
& $node '<test-dir>\work\_probe-rewrite-samesize.mjs'
```
**真实输出（关键行，`_probe1-out-final.log`）**
```

文件字节数 S = 5377 （V1=V2=V3）
前缀字节数 = 4857 （>4096，故尾帧变化落在头部指纹窗口之外）
前 4096 字节 = V1/V2 相同: true | V1/V3 相同: false
sha256(V1)= 87ef85a830085262 sha256(V2)= ec28aff120e71b9b | 整文件相同? false

[run1 · V1] stat: {"written":2,"skipped":0,"unchanged":0,"identityRewrites":0,"newTurns":2}
[重写] 写入 V2：size=5377（与 V1 相同=true）
[run2 · V2] stat: {"scanned":1,"written":0,"skipped":2,"unchanged":1,"identityRewrites":0,"newTurns":2,"incremental":0}

[对照 run3 · V3] stat: {"written":0,"skipped":2,"unchanged":0,"identityRewrites":1,...}

```
**结论一行：MISSED 成立 —— 源文件被"同字节数、前 4096 B 相同、后段换内容"重写时，`headFingerprintBytes` 发现不了，`unchanged=1`，台账仍是旧内容（`ledgerTurn2StillA=true`），而源文件已经是新内容（`sourceNowB=true`）——新内容永久漏记。**

**边界补充（读代码 + 对照）**
- 这不是"没修"：P0-1 修的是"文件变小仍走 unchanged"和"同大小但头部也变"两类；**头部窗口之外的同大小重写不在该修复覆盖范围内**（`sameIdentity` 的语义就是"头 N 字节相同"）。
- 窗口大小可配（`headFingerprintBytes`，clamp 64–1 MiB），但无论配多大，只要重写不触及被取样的那一段、总字节数不变，就漏。
- 现有用例 `P0-1b`（同大小重写）之所以能过：它的构造里 V1/V2 的**帧头内容尺寸不同**，差异落在默认 4096 窗口内/边界上；它不是本探针的形态。`P0-1c` 也明确把 `headFingerprintBytes` 压到 256 才能覆盖"缩小后又长回"的形态。
- 本条已由项目侧记入 `05-已知未覆盖项.md` 明账；**修复方式不由本材料裁定**。

## 探针 2 · 库外锚链：断链能判红，但"定位"与"整链重写"是两回事

**要复现的边界**：`lib/manifestanchor.js` 的 `readAnchor()` 校验 `kind==='package'` 行的 `prevHash === 上一行.payloadHash`；`verifyPackageAgainstAnchor()` 把链作为一项 checks。问题：① 断链时 `breaks[].at` 指的是**断点行**还是**被改行**？② 如果改中间行并把后续 `prevHash` 同步改掉（整链一致重写），还能不能发现？

**构造（现场造数）**
```
临时锚目录；用 appendAnchor() 造 3 条 package 锚（0.9.1 → 0.9.2 → 0.9.3，prevHash 首尾相连）
① 基线：readAnchor().chainOk 应 true；verifyPackageAgainstAnchor(0.9.3) 应 true
② 只改第 2 行 payloadHash（其余字节不动）
③ 改第 2 行 payloadHash + 把第 3 行 prevHash 同步改成新值（"整链一致重写"）
```
**命令**
```powershell
& $node '<test-dir>\work\_probe-anchor-chain.mjs'
```
**真实输出（关键行，`_probe2-out.log`）**
```
锚文件行数 = 3 | 每行 payloadHash: 0.9.1=29b5b958f3dc , 0.9.2=55a393f8d77c , 0.9.3=e5a162351b2f

[① 基线] readAnchor: chainOk = true | entries = 3 | breaks = []
[① 基线] verifyPackageAgainstAnchor(0.9.3): ok = true | checks = anchor-exists:true anchor-no-bad-lines:true anchor-chain:true manifest-no-bad-lines:true package-anchored:true payloadHash:true manifestSha256:true manifestCount:true fileCount:true

[② 改中间一条 payloadHash]
  readAnchor: chainOk = false
  breaks = [{"at":3,"version":"0.9.3","expected":"55a393f8d77c02b4a0fdf7dce66d0458ffffffffffffffffffffffffffffffff","actual":"55a393f8d77c02b4a0fdf7dce66d0458c945f6d0acc07299817091c28d27aa31"}]
  → breaks[0].at = 第 3 行（被改的是第 2 行）
  verifyPackageAgainstAnchor(0.9.3): ok = false | anchor-chain = false
  verifyPackageAgainstAnchor(0.9.2 自身): ok = false | payloadHash = false | chain = false

[③ 整链一致重写]（改第 2 行 payloadHash + 第 3 行 prevHash）
  readAnchor: chainOk = true | breaks = []
  verifyPackageAgainstAnchor(0.9.3): ok = true | checks = …（9 项全 true）
  锚文件 sha256 变了 = true （基线 db1270d429494271 → 现在 4c714a979395d8b7）

>>> 判定：BREAK-DETECTED（判红；但 breaks[0].at 指向断点行 3，不是被改行 2；且整链一致重写后 chainOk=true，无法发现）
```
**结论一行：① 单行篡改确实判红（`verify.ok=false`）；② 但 `breaks[0].at` 指向"断点行"（第 3 行）而不是"被改行"（第 2 行）；③ 只要把后续 `prevHash` 一起改（整链一致重写），`chainOk` 回到 `true`、9 项 checks 全 true——链本身发现不了，只有一个"变了"的锚文件 sha256 能看出来，而那个基线必须存在库外。**

**边界补充**
- `readAnchor()` 只校验相邻两行关系；**没有对每行内容本身做 hash/签名**。所以链的语义是"这一行接得上上一行"，不是"这一行没被换过"。
- `verifyPackageAgainstAnchor()` 的 `anchor-chain` 检查是链，不比对"外部留存的锚基线"。
- 要发现"整链一致重写"，需要库外基线（另机/纸面记录的锚文件 sha256 或逐行 payloadHash）。这正是 21-B.3 的条件。
- 现场还验证了：改第 2 行后 `verifyPackageAgainstAnchor(0.9.2 自身)` 也判红（payloadHash + chain 双红）——说明"当前包自身 vs 锚"这条链能挡住"包被换"。
