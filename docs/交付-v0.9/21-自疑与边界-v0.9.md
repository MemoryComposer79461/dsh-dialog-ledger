## A · 采集换轨（shadow 双通道：disk ↔ persistence）

### A.1 能证明什么

**【动态证实】**
1. 现场复跑 `docs/自测-collector.mjs` **10/10**、`docs/自测-shadow.mjs` **15/15** 全绿（2026-11-11，见 20-§一 D3）。覆盖：disk collector 只读；persistence collector 的 `list/open/read(seq)` 增量、EOF、关句柄、异常降级不抛；`turnFingerprint` 稳定；`compareTurnSets` 四类差异可判；`closedTurnsFromEvents` 与磁盘口径一致；R-01 影子只写 `.shadow/`；R-04 连续 3 轮 collector 抛错只产生 warnings、不拖垮记账；R-06 默认 `disk` 时完全不跑影子；R-09 模式切换不改账；R-02b 增量读第二轮不产生假差异；R-08 `maxSessions` 生效；R-10 影子证据可离线复核。
2. 真机观测（历史记录，本次未复跑）：`docs\验收-v0.7\影子真机观测-20261110.md` 记录 `ingest.mode=shadow` 下连续 2 轮 **checked=11 / exactMatch=11 / diffCount=0 / warnings=0**。同一文件自述"本轮为首次真机采样，不作最终放行结论；R-03 需连续多轮（建议 ≥6h）"。

**【静态推断】**
3. "不一致时以谁为准"在当前实现里是**固定的设计口径**：`index.js` 的影子 tick 用 `createDiskCollector()` 做 disk 侧读、`createPersistenceCollector()` 做另一侧读；主记账路径（`runOnceCore` → `readSourceTurns`/`legacy` 磁盘扫描）**不读影子结果**。影子只把差异写进 `<root>/ledger/.shadow/`。
4. 配置枚举接受 `disk | shadow | persistence | event` 四值，但代码搜索无事件采集器（无 `createEventCollector`）；任何非 `disk` 值都只是"跑影子"。

**结论句**：现在能证明的是「**disk 通道写的账没有被影子偷偷改写；影子能逐会话报告轮次边界的一致/不一致**」。这就是全部。

### A.2 不能证明什么

1. **不能证明"换轨发生了"。** 能写账的仍只有 disk 通道；B（持久层）只做影子；A（事件主通道）在 lib 里**没有实现**。所以"三态采集"目前实际是"**1 写 + 1 影**"，不是三态。任何"已切换/已双轨"的表述都不成立。
2. **不能回答审计需求书那句"不一致被发现之前，谁知道账记的是哪条通道的结果"。** 答案在设计上是"永远是 disk"；但这只是口径，**没有测试验证过"persistence 对、disk 错"时会发生什么**——因为根本没有这条路径（不告警、不回填、不记入账）。
3. **不能证明"两侧内容一致"。** 双通道比对单元是轮次边界指纹：`sha256(fpVersion|sid|turn|startMs|endMs|reason)`——**不含正文、事件内容、附件**。同一边界、不同正文 → `exactMatch=true`。它证明"两侧数出来的轮次一样"，不证明"账记得对"（"记得对"这一层目前只由磁盘路径上的双实现复核器覆盖，见 20-表·双实现复核器行）。
4. **不能证明"一致率达标"。** R-03（差异归零会话 ≥99%）是判据映射表 8 条**无主**之一；真机样本只有 2 轮 / 11 会话；长跑没有发生。
5. **视野有界。** 影子默认最多比对 50 个会话（`ingestShadowMaxSessions=50`）；`pendingWindowMs=120000` 内"另一源有、磁盘还没有"被归为**良性领先**（`pendingDurable`），窗口内的漏记在影子里不算差异。
6. **持久层 API 形状没有全量真机验证。** collector 对 `events/data/items/数组` 四种返回做防御性归一，代码注释自认"形状待真机 V1/V2 验证后收紧"；测试用 fake host。真实宿主形状若不同，失败会**降级成 warnings 而不抛**——即"坏了，但不报账"。
7. **【只能由作者保证】** 指纹字段为什么是这 5 个（sid/turn/startMs/endMs/reason）、120s 窗口为什么合理、99% 阈值从哪来、`pendingDurable` 的"良性"定性——都是设计选择。测试只能证明"按这些选择实现且自洽"，不能证明"这些选择对"。
8. **换轨这件事没有"作者以外"的验证。** 比对口径、差异四分类、fpVersion 全由同一作者定义；外部无法判断"mismatched 该算严重还是正常"——需要契约/审计方裁定。

### A.3 需要什么条件才能证

| 要证的东西 | 可执行的取证条件 |
|---|---|
| 双通道在真实宿主下能对齐 | 真宿主、`ingest.mode=shadow`、真实会话、真实 persistence API，**连续 ≥6h**；每 tick 留 `.shadow/summary.json`；R-03 每条差异写白名单理由。这是 V1.0 门槛，不是本轮能做 |
| 两侧"内容"也一致 | 把 **docSha256/原文逐字/事件内容哈希**加入比对单元（现在只比边界指纹），再跑同一批会话 |
| "不一致时以谁为准"有答案 | 写一份**事实源规则**（disk 写 / persistence 只读审计 / 冲突时谁告警、谁回填、谁签字），并配 3 个测试：disk 少一轮、persistence 少一轮、同轮不同内容 |
| 换轨可切换、可回滚 | 实现 A 事件通道 + 切换演练（disk→shadow→persistence→回滚），每一步断言"账按规则不变或按规则变"，并留切换证据 |
| 四种 mode 行为可解释 | 对 `disk/shadow/persistence/event` 四值各跑一遍，断言产物差异（目前后两值只等于 shadow） |

## B · 库外锚链（manifestanchor.js：payloadHash / MANIFEST / prevHash）

### B.1 能证明什么

**【动态证实】**
1. 现场复跑 `docs/自测-manifestanchor.mjs` **5/5 全绿**（其中 MA-02 **空过**，见下）：MA-01/03/04 append-only + fsync + 幂等 + 包校验 + **改包内文件 → payloadHash 判红**；MA-05 prevHash 断 → 链校验判红并给出 `breaks`；MA-06/07 账本快照篡改一日 → 判红、校验器**只读**（整树哈希不变）；MA-08 index 接锚（每日快照一次 / 包锚幂等 / 锚目录在库内 → `ANCHOR_INSIDE_ROOT` 拒绝）。
2. **探针 2**（现场造 3 条 package 锚）：基线 `readAnchor().chainOk=true`、`verifyPackageAgainstAnchor(0.9.3).ok=true`（9 项 checks 全 true）；改中间一条 payloadHash → `chainOk=false`，`breaks=[{at:3, expected:…, actual:…}]`；同一构造下 `verifyPackageAgainstAnchor(0.9.3).ok=false`。
3. 现场解析交付锚文件：`DELIVERY-ANCHOR.jsonl` 共 **5 条 = 4 条 package + 1 条 ledger-snapshot**，4 条包锚的 `prevHash` 首尾相连。

**结论句**：现在能证明的是「**锚文件没有被局部涂改；包内容与锚记录的 payloadHash 对不上会被发现（前提：锚自身可信）**」。

### B.2 不能证明什么

1. **"三处独立证据"其实是同源。** payloadHash 算法只有一份实现：出包脚本算一次，`manifestanchor.computePackageDigest()` 复算一次，**同一个算法**；包内 MANIFEST 由同一套脚本生成；锚记录的是**期望值**，不是"独立算出来的值"。所以审计需求书问的"如果它错了，那三处独立证据会不会一起错"——答案是**会**。三处的"独立"只在**位置**（库内 MANIFEST / 版本台账 / 库外锚），不在**计算**。
2. **算法正确性只能由作者自己保证。** 测试能证明"复算结果 = 台账里记的期望值"，但期望值也是同一实现写的。唯一的"外证"是拿真包的 payloadHash 与其他记录对齐——而这条（MA-02）在本次环境里**空过**：
   ```
   [SKIP] 0.7.0 真包不存在（异机/清理后可跳过）
   ✔ MA-02：computePackageDigest 算法与出包脚本/台账一致（1.36ms）
   ```
   即：**"payloadHash 与版本台账一致"这一条，本轮没有被真正执行，却在全绿里计了 pass。**
3. **链没有对每行内容自证。** 探针 2 ③：改中间一行 payloadHash，同时把下一行 prevHash 改成新值（"整链一致重写"）后，`readAnchor().chainOk=true`、`verifyPackageAgainstAnchor(0.9.3).ok=true`——**校验器发现不了**。链只保证"相邻两行接得上"，不保证"这一行还是原来那行"。
4. **断链定位指向"断点行"，不是"被改行"。** 探针 2 ②：被改第 2 行，`breaks[0].at=3`（第 3 行的 prevHash 对不上）。定位信息足够"从这里开始不信"，但**不能直接指名被改行**，要人再回看前一行的来源。
5. **"库外" ≠ "不可改"。** 锚文件在桌面，U 盘也是可写介质；没有签名、没有可信时间戳；能改文件的人可以**整链重写**（探针 2 ③ 已证明校验器看不出来）。要发现这类改写，必须有一份**不在这块盘上**的基线（例如每次都把锚文件 sha256 抄到另机/纸面）——目前没有。
6. **锚的覆盖范围有限。** 只锚：交付包（payloadHash/manifestSha256/文件数）+ 账本快照（日台账文件 sha256/bytes/rows + 周账计数）。**不锚**：清册、journal、完整原文、读日志、影子证据。`ledger-snapshot` 行在 v0.8 格式里 payloadHash 恒为空，只做**结构校验**，逐文件复算只在"恢复演练"工具里做。
7. **恢复演练"通过"证明的是自洽，不是正确。** `docs\验收-v0.8\恢复演练-0.8.0-U盘目录.md` / `…U盘zip.md` 记录 PASS（manifest-check 426/426、锚链连续、payloadHash 一致），但演练脚本调用的仍是同一套 `manifestanchor`——它证明"包 + 锚自洽、能被复算出来"，不证明"内容就是当时交付的那一版"。
8. **【静态推断】两条未测边界**：`verifyPackageAgainstAnchor` 选锚条目时含 `pkgDir.includes(version)` 的**版本子串匹配**（0.9.1 / 0.9.10 这类前缀混淆未测）；`appendAnchor` 的幂等只比对**最后一条** package 锚（更早的重复仍可再追加）。
9. **【只能由作者保证】** `prevHash` 链以 payloadHash 为负载的语义、"创世"标记允许 `''` 与 `（创世）` 两种写法的约定、payloadHash 排除 `MANIFEST.sha256 / 版本台账.md / 00-交付清单.md` 三个自指文件的规则——都没有第二实现对照。

### B.3 需要什么条件才能证

| 要证的东西 | 可执行的取证条件 |
|---|---|
| payloadHash 算法没算错 | 由**审计方独立实现**一份 payloadHash（只按书面规则），对 0.8.0 / 0.9.0 包复算，与锚、版本台账三方对齐；不一致时先裁定规则再动锚 |
| 锚没被整链重写 | 每次出新包，把**锚文件 sha256**（最好连同 payloadHash 序列）记录到库外（另一台机器/纸面/U 盘只读区）；比对时先比这份外部基线，再跑链校验 |
| 链能自证到"行级" | 若产品要求"无人值守也可信"：每行自身 hash 入链 / 签名 / 可信时间戳。这违反"零依赖、不联网"红线，需产品决策，不能偷偷加 |
| 覆盖清册与 journal | 把清册/journal 的文件 sha256 纳入 `ledger-snapshot`（或在锚里新开 kind），恢复演练里一起复算 |
| MA-02 真正执行 | 在有 0.7.0（或 0.9.0）真包的环境复跑；并把"真包不在"从 `return`（计 pass）改成 `t.skip` 或显式 fail，**禁止空过** |

### C.2 不能证明什么

1. **只证明了"已知的一条路径"。** 越界防护覆盖的是 `getTurn` 的 `doc`/原文候选路径（`containedPath`）。工具面里**由数据决定路径的其他位置**是否都有同等防护，要逐条看：`cleanup_preview/apply` 走 `listOriginals/planCleanup`（按布局规则扫第 3 级目录，不经 `containedPath`；目录联接/符号链接跳出未测）；`ledger_anchor` 读 `anchorRoot`（只有 `isSafeRoot` 的"绝对路径 + 非盘符根"检查，**不是**包含性校验）；面板 other 路由另有纵深但未逐条验证。所以不能说"全工具面路径安全"。
2. **路径修了，参数面/权限面没修。** `excerptBytes` 仍无上限（只被文件大小截断，同步 `Buffer.alloc`）；`sid`/`keyword` 无长度限制（`keyword` 是全表 `includes` 扫描）；**没有调用者隔离**——任何 Agent 都可以用任意 `sid` 查任意会话，`whoami` 只是自报，不是鉴权；读日志记了工具/参数/命中/字节/耗时，**不记实际读取的绝对路径，也不记 `rejected`**——越界尝试在读日志里看不出（修后仅在工具返回值里可见）。
3. **9 个工具面：进程内成立，真宿主未验。** 落稿时 `lib/toolface.js` 已接 **9 个工具**、`docs/自测-agenttools.mjs` 15 例、`自测-toolface.mjs`/`自测-toolcards.mjs` 已按 9 工具更新，现场 **27/27 全绿**——但这证明的是"**进程内 `buildToolDefs` 定义 + `execute` 行为 + apply 时注册 9 个**"。**没有**的是：真宿主里实际挂载 9 个工具、启动诊断 `registered=9`、冷启动一次的证据（A13 是 V0.6 一次性真机证据）。此外 AG/CT 用例全部用**合成夹具**，不覆盖真实账库形态。
4. **三重条件防"手滑"，不防"算对了再删"。** 探针 3B 的边界：confirm 只绑定 `planned + reportId`，**不绑定内容哈希**——同码同名换内容后 confirm 仍匹配并真删（现场已验证）；`preview → apply` 之间**没有锁/没有计划指纹**，靠"重算 planned"挡住数量变化，挡不住"同名同数换内容"；confirm 字符串可由模型根据 preview 返回值自行拼出——它防的是"旧计划/错字"，不是"恶意或误判"。
5. **工作流约束只是提示。** "先 `ledger_whoami`、先 preview 再 apply"写在工具描述里，是**提示**不是 guard；模型可以跳过 preview 直接构造 confirm（只要它算得对）。
6. **真宿主挂载没有自动化。** A13"重启后 mounted"是 V0.6 的一次性真机证据（当时 5/7 个工具）；"9 工具挂载 + 冷启动 + registered=9"落稿时未验。
7. **【只能由作者保证】** `confirm` 短语格式 `DELETE <planned> <reportId>` 是否足够让"人"看懂、读日志字段是否足以支撑"重审计"、工具返回的紧凑度是否会误导模型——这些是设计选择，测试守不住。

### C.3 需要什么条件才能证

## 收尾：三句话

1. **A（采集换轨）现在只有"1.5 态"**：disk 唯一写者 + persistence 影子；A 事件通道没有实现，换轨没有发生。它证明的是"影子看得到边界差异"，不是"账记得对"。
2. **B（库外锚链）的根仍然是同源的**：算法、MANIFEST、锚记录出自同一实现，链只保证相邻接得上。**整链一致重写发现不了**——这条只能靠库外基线（另机/纸面）补，补不了就只能照实写"信任根由作者自证"。
3. **C（Agent 工具面）刚补上一条真实的边界**：越界读取已被 `containedPath` 关上并留痕（修前/修后现场对照）；9 工具/清理三重条件在**进程内**已有 27/27 现场证据；但 9 工具的**真宿主挂载**、`containedPath` 之外的路径（清理目录扫描、`anchorRoot`）、参数上限、权限面仍**没有动态证据**；三重条件防手滑不防误判，confirm 不绑定内容哈希。

**以上三节中，"不能证明什么"里的每一条，都不应被读成"将来会修"；在它被证到之前，它就是"现在还不知道"。**
