# 03 · 周账两态 + 补记执行器设计（V0.7.x）

> 依据：机主《项目批复-记忆插件v0.6.1》补 3——"周账那条要改两次：①草稿/封板单文件两态（草稿前缀 + rename 封板；对账/收据只认正式名）②补记执行器（先有 journal + 幂等 + 回退）"。
> 状态：**设计定稿（2026-11-10）**；实施分三小步，先状态机/命名/兼容（本文件），再写入路径切换，再补记执行器。

## 一、现状（v0.6.7）

- 周记账文件名固定 `MM月第W周-{S}{D}的周记账.xlsx`（`lib/week.js weeklyFileName`），**草稿与封板同用正式名**；
- `writeWeekly()` 每轮按草稿内容重写该文件；封板时把"已封板"标记写进同一文件 + `weekly-seal` journal 事件；`SEALED_STATUS_TEXT` 用于事后识别；
- 补记册（overflow 行）由 `writeWeekly` 内直接写 `weekly-supplement`（补记编号/hash 链），已有 BC-01…BC-15 判据；
- `backfillPlan()` 只读计划存在，**执行器未接线**（v0.5 05 #15；run-report 以 `backfillExecuted=false` 留痕）。

## 二、目标状态机（单文件两态）

```
        ┌──────────────┐   生成/重写（可反复）    ┌──────────────────┐
        │  草稿 draft  │ ───────────────────────▶ │ 草稿-<正式名>.xlsx │
        └──────┬───────┘                          └──────────────────┘
               │ 封板（到封板时点）
               ▼
        ┌──────────────┐   一次性写入封板内容到临时文件
        │ 封板 sealed  │   → fsync → rename 成正式名（<正式名>.xlsx）
        └──────┬───────┘   → 删除草稿文件（若存在）
               │
               ▼
        【不可回退】正式名文件不再重写；对账/收据只认正式名
```

规则：
1. **草稿**：文件名为 `草稿-` + 正式名，内容状态行 = `DRAFT_STATUS_TEXT`；每轮可重生成/重写（可被覆盖、可删除）。
2. **封板**：内容状态行 = `SEALED_STATUS_TEXT` + `封板hash:`；**先写临时文件 → fsync → rename 为正式名**；成功后删除同名草稿；`weekly-seal` journal 记录 `file` = 正式相对路径。
3. **正式名文件一旦存在即视为封板**（内容必须带封板标记；出现"正式名但无标记"= 历史遗留草稿 → 迁移规则见 §四）。
4. 对账/收据/清册/面板"周账"计数**只认正式名**；草稿存在 ≠ 周账已出。
5. 封板后**绝不**重写正式名文件；补记只走补记册（第二写入口）。

## 三、读取端兼容矩阵（需要改的检查点）

| 模块 | 现状 | 两态后 |
|---|---|---|
| `lib/weekly.js writeWeekly` | 写正式名（草稿内容） | 草稿 → `草稿-` 路径；封板 → 临时 sealed 文件 rename 正式名 + 删除草稿 |
| `lib/reconcile.js`（周账存在性） | 只查正式名存在 | **保持**只认正式名（草稿不满足"已出周账"） |
| `lib/selfheal.js`（缺 xlsx 判定） | 查正式名 + 标记区分 | 正式名缺失：若草稿存在 → action=`weekly-draft-regenerate`（草稿可重建）；若 journal 有封板 → `sealed-missing`（不可重建） |
| `lib/panelapi.js` / `lib/catalog.js`（周账计数） | 扫 `NN月第W周-…xlsx` | 正则排除 `草稿-` 前缀（只统计正式名）；面板可另给 `draftCount`（非账） |
| `lib/receipt.js`（收据锚） | 正式名 | 保持正式名 |
| `checkup` / `sealcross` | 正式名/封板 journal | 保持；草稿不参与交叉核验 |

## 四、历史文件迁移（一次性、可审计）

| 情形 | 判定 | 动作 |
|---|---|---|
| 正式名 + 有封板标记（或 journal 有该 gid） | 已封板 | **不动** |
| 正式名 + 无封板标记 + journal 无该 gid | 历史遗留草稿 | 首轮：rename 为 `草稿-<正式名>`（文件字节不动），再按草稿重生成；rename 失败 → 告警跳过，不阻塞 |
| 正式名 + 草稿名同时存在 | 冲突 | **保正式名（视为封板证据）**、告警 `E_WEEKLY_STATE_CONFLICT`，不删除任何一方 |
| 只有草稿 | 正常草稿 | 直接重写草稿 |
| 正式名存在但内容无标记且 journal 有 gid | 矛盾 | 告警 `E_WEEKLY_SEAL_MARKER_LOST`（Excel 重存可能擦标记，05 已知），**不重写** |

迁移只做 rename（不改字节），旧文件不重命名以外的任何操作；迁移决策为纯函数（`lib/weeklystate.js`）便于测试。

## 五、补记执行器（第二写入口）

```
backfillPlan(root)  ──只读计划──▶  plan.actions[]
                                      │
                    executeBackfill({root, actions, dryRun})
                                      ├─ 写 .backfill-journal.jsonl（先证据后动作，append+fsync）
                                      ├─ 幂等：actionKey = sha256(kind|target|fingerprint)
                                      │   已 applied/committed → skip（计数 dupSkipped）
                                      ├─ 执行：可逆动作（草稿重生成/补记册追加）→ 立即 fsync
                                      ├─ 失败：journal 记 failed；下轮按 key 重试（有上限）
                                      └─ 回退：只回退"未提交"动作；已提交的账行不可删
                                         （journal 记 compensation 事件，账本追加"作废/更正"行需机主批）
```

- journal 字段：`v, at, actionKey, kind, target, status:'planned'|'applied'|'failed'|'skipped'|'compensated', attempt, detail, hashBefore/hashAfter?`；
- **幂等键**不含时间戳（同输入同 key）；
- 回退语义按上：`planned` 可撤销（未执行）；`applied` 不可撤销（append-only），只能记补偿事件并人工批"作废/更正"；**不静默改历史**；
- 与周账两态的交点：`weekly-draft-regenerate` 只动草稿文件；`overflow-seal` 写补记册（已有 hash 链）；绝不改正式名。
- 判据草案：`BE-01` journal 先于动作；`BE-02` 幂等（重复执行 0 新增）；`BE-03` 失败可重试且金额/行数不重复；`BE-04` 草稿动作不改正式名字节；`BE-05` 回退只撤 planned；`BE-06` run-report 暴露 executed/dupSkipped/failed/compensated。

## 八、与 KERNEL / 审计的关系

- KERNEL 六文件（ledger/frames/sealjournal/pending/lock/week）**不动**；本设计只改周账写入层与运行报告字段。
- 封板 journal 语义不变（仍 append-only、canonical hash）；两态只改"文件何时以何名出现"。
- 旧账本/旧周账**零迁移改写**；迁移仅对"无封板标记的正式名草稿"做 rename。

### 十、补记执行器实施进度（第 7 轮，2026-11-10）

- ✅ 新增 `lib/backfill-exec.js`：
  - **证据先行**：每个动作先追加 `<root>/ledger/.backfill-journal.jsonl`（append+fsync）`planned`，再执行，成功/失败再追加 `applied`/`failed`；
  - **幂等**：`actionKey = sha256(规范化 kind+目标)`；journal 终态（applied/deferred/gave-up/compensated）→ 下一轮 skip；

  - **证据不完整即停手**：journal 有坏行 → 拒绝执行并报 `JOURNAL_BAD_LINES`；
  - handler：本版已接 `write-supplement`（复用 writeSupplement 的只追加/幂等）；`backfill-missing-turns`/`promote-pending` 记 `deferred: handler-not-wired`（留痕不假执行）。
