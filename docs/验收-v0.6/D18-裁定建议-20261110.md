## 二、为什么建议接受（三个理由，对应三条审计原则）

1. **闸门必须有区分力**（否则报警器退化成常亮灯，人会开始无视它）。
   不接受 D18 → 任何含历史行的老账库 `okStrict` 永远 false → 闸门对老库不可用。
2. **D18 不放宽任何防线**：`CH-01`（历史行永不 bound）不变、周账四态不变、`ok` 公式不变。
   变的只是"文件在但没绑定证据"这一种情况**从缺凭证里单列出来**，而且仍然逐条可见。
3. **风险面已被条件锁死**：只有"问题**仅**含 `LEGACY_NO_ATTACHMENT` + 附件不缺"才归 legacy；
   哈希不符 / 路径不符 / 附件不符 → 仍进 `originalMissing`（篡改和损坏不会被洗白）。

## 三、我建议的裁定文本（可直接抄进契约增补 v0.6.1）

> **D18 接受**：`reconcile()` 输出单列 `legacyUnverifiable[]` / `legacyUnverifiableCount`；
> 此类行**不计入** `originalMissing`，但**必须**在运行报告、对账文本、面板中逐项可见；
> `ok` 公式不变；`CH-01` 不变。

### 8.1 A 的第一步就把一个真漏洞照出来了

实证探针（`<test-dir>\work\_probe-disguise.mjs`）：复制语料账库 → 把一条 v0.5 台账行的
`docFileSha256 / docSha256 / attachment / turnState` 删掉（只留 v0.4 时代就有的字段）→ 跑 `reconcile()`：

```
该行在 legacyUnverifiable = true
该行在 originalMissing  = false        ← 不计缺凭证
>>> 【攻击成功】删掉证据字段后，该行被当成 legacy（未计缺凭证）
```

**结论：D18 初版"按缺字段判定 legacy"存在洗白通道。** 只补一条测试（而不改设计）就是自欺。

### 8.2 修正设计：legacy 只能由"正面证据"确认

- 新增 `<root>/ledger/.legacy-marks.jsonl`：**append-only + 哈希链**（`prevHash` 接上一条 `hash`），
  由一次性工具 `docs/工具-标记legacy基线.mjs` **显式**写入（默认 dry-run，必须 `--write`）。
- 每条基线记录 `{code, rowFingerprint}`；`rowFingerprint` = 台账行稳定序列化（键排序）后的 sha256。
- `reconcile()` 判定：视图文件在 + 仅缺证据 + **基线标过且指纹未变** → 才算 `legacyUnverifiable`；
  - 未标记的无证据行 → `originalMissing`（`reason:'NO_BINDING_EVIDENCE'`）→ **压 ok**；
  - 标记过但行变了 → `mismatched` → 仍按缺凭证计；
  - 基线链断 → `chainOk:false`，且不得把行算 legacy。
- 工具幂等：同 code 同指纹重复 `--write` 只跳过；同 code 不同指纹 → **冲突，不覆盖**（退出码 2）。

### 8.3 B：让 legacy 口径"看得见"

- 运行报告 `counts`：`legacyUnverifiable` / `legacyUnmarkedNoEvidence` / `legacyMarksMismatched` / `legacyMarksChainOk`；
- 只读 API `summary.health`：`legacyUnverifiable` / `legacyUnmarkedNoEvidence` / `legacyMarksChainOk`（无报告 = null）；
- 面板健康度第一屏：新增「历史无证据」「未标记无证据」两项指标；
- 对账文本：已标记 / 未标记 / 指纹不符 / 链断 四类明示。
