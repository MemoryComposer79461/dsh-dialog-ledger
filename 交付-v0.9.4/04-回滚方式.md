# 04 · 回滚方式 · `v0.9.4`（lite 线）

> 原则：**回滚的是代码，不是账。** 账本 `ledger/*.jsonl` 只追加、不回改；本版**不迁移旧库、不改台账行格式（`v:3`）、不改数据总库布局（`lib/layout.js` 未动）、不新增配置键**——所以回滚只需要换代码，账库一个字节都不用动。
> 本版新增的都是**派生件**：`ledger/.index/`（索引，可由台账重建）、`YYYY年MM月/MM月账.md`（视图，可重建）、`ledger/.tick-metrics.jsonl` 的新键（运行度量）——**可留可删**（§三）。
> 依据：`VERSION.json`（`baselineTag=lite-v0.9.4-snap`、`rollback=git reset --hard lite-v0.9.4-snap`）；tag/提交/快照数字均为写作时**现场实测**（`git rev-parse` / `git ls-tree -r -l` / `_工作\snapshots\*\snapshot.json`）。

> 读法：tag 指向的是"记录提交"（把代码提交哈希写进 `VERSION.json`/`版本台账.md` 的那次），**tag 提交 ≠ 代码提交**：
> - `lite-v0.9.4-snap` = `3636378`，其代码提交是 `1d30840`；
> - `lite-v0.9.4-re1` = `faadebb`，其代码提交是 `2f6b5af`。
> 树内容只差元数据（`VERSION.json`、`版本台账.md` 的哈希/行）。"看代码"用代码提交；"复位到某版"用 tag。

> **快照现状（本版比 0.9.3 好）**：`_工作\snapshots\` 下现有 **4 份**目录快照——`v0.9.3`（461/6,982,189）、`v0.9.3-re1`（456/6,868,175）、`v0.9.4-snap`（467/7,271,120）、`v0.9.4-re1`（471/7,545,125）；所以动作③对 snap/re1 都有素材（0.9.3 时只有 re1 一份）。0.9.2 及更早**无快照**，只能走动作①。

## 二、三种回滚动作

先设两个路径变量（下同）：

```powershell
$git  = '<build-host>\_工作\tools\MinGit\cmd\git.exe'
$repo = '<build-host>\_工作\lite'
```

### ① `git reset --hard`：整树退回上一版（默认动作）

```powershell
& $git -C $repo rev-parse HEAD                  # 先记下当前 HEAD（本版应为 faadebb…）
& $git -C $repo status --short                  # 先确认工作区干净（本版：空；交付-v0.9.4 为未跟踪）
& $git -C $repo reset --hard lite-v0.9.4-snap   # 退回开工前（$VERSION.json.rollback）
& $git -C $repo rev-parse HEAD                  # 期望 3636378…
& $git -C $repo reset --hard lite-v0.9.4-re1    # 复位回本版（HEAD 回 faadebb）
```

- 期望：HEAD 从 `faadebb` 变为 `3636378`；`VERSION.json.type` 变 `snap`；`cordis.patch.yml` **仍是 `scanBudgetMs: 30000`**（0.9.4-snap 与 re1 配置逐字节相同，不像 0.9.2→0.9.3 那样回退默认值）；`git status --short` 只剩未跟踪的 `交付-v0.9.4/`（未跟踪文件不会被 `--hard` 删除）。
- 代价：丢弃**已跟踪文件**的未提交修改；不删除未跟踪文件（`交付-v0.9.1/02/03/04/` 是已跟踪目录，`--hard` 会把它们恢复成目标版本中的样子；`交付-v0.9.4/` 不在任何旧 tag 里，属未跟踪，保留）。
- 本仓库 `core.autocrlf=false`（0.9.1 实测；本版未改），复位**不做换行转换**，工作区字节与提交一致。
- 退回 0.9.3 正式版：`& $git -C $repo reset --hard lite-v0.9.3`（HEAD 变 `413f184`；`VERSION.json.version=0.9.3`、`type=formal`；测试基线回到 **504/460/44**；判据回到 C01–C18；**索引/月账/备份工具从代码里消失**，但盘上 `.index/`、`MM月账.md` 仍在——旧代码不读）。
- 退回 0.9.2 正式版：`& $git -C $repo reset --hard lite-v0.9.2`（HEAD 变 `71f259c`；测试基线 504/460/44；`scanBudgetMs` 回到 **3000**；内核检查仍 PASS）。
- 复位回本版：`& $git -C $repo reset --hard lite-v0.9.4-re1`（HEAD 回 `faadebb`）。

### ② `git checkout <tag> -- .`：只取文件，不动分支指针

```powershell
& $git -C $repo checkout lite-v0.9.4-snap -- .
# 或只退单个文件（例：只把 index.js 的索引接线退回去，保留 backup/pointerindex 代码）
& $git -C $repo checkout lite-v0.9.4-snap -- index.js tools/pointerindex.mjs
```

- 期望：工作区文件变成目标 tag 内容，HEAD 不变，`git status` 显示一堆"已修改"——这是**故意**的，用于"只拿旧文件比对/临时跑一下/只退一个模块"。
- 注意：`checkout -- .` **不会删除**目标 tag 里不存在的文件（例如 `docs\判据-0.9.4.mjs`、`docs\工具-设备自检.mjs`、`docs\自测-094-*.mjs` 在 snap 里不存在，会留在盘上；**但此时 `index.js`/`docs` 入口已退回旧版，不会 import 它们**，属"死文件"，不影响运行；要干净复原请用 ①）。
- 想恢复成 HEAD：`& $git -C $repo checkout HEAD -- .`。

### ③ 目录快照恢复（不走 git；最接近"逐字节复原"）

**前提（重要）**：快照树里**没有 `.git`**（`_工作\tools\snapshot.mjs` 的 `copyDir` 跳过 `.git`），`snapshots\v0.9.4-re1\tree` 是**整仓 471 文件**（含 `交付-v0.9.1/`～`交付-v0.9.3/`、`MANIFEST.sha256`），**不含本版 `交付-v0.9.4/`**（快照早于交付五件）。所以：

**不要**直接把快照 `robocopy /MIR` 到 `_工作\lite` 根目录——`/MIR` 会**删掉 `.git`**（仓库历史和 tag 全没），也会删掉本版 `交付-v0.9.4/`。正确做法二选一：

```powershell
# 方案 A（推荐）：在副本目录里恢复与校验，不碰工作仓库
$snap = '<build-host>\_工作\snapshots\v0.9.4-re1\tree'
$dst  = '<build-host>\_工作\回滚演练B\v0.9.4-re1'   # 或任意空目录
robocopy $snap $dst /MIR /NFL /NDL /NJH /NJS

# 方案 B：原地恢复（先移出 .git 与交付-v0.9.4，再镜像，最后放回）
$lite = '<build-host>\_工作\lite'
Move-Item "$lite\.git"          '<build-host>\_工作\_tmp-git-暂存' -Force
Move-Item "$lite\交付-v0.9.4"   '<build-host>\_工作\_tmp-交付v094-暂存' -Force
robocopy $snap $lite /MIR /NFL /NDL /NJH /NJS
Move-Item '<build-host>\_工作\_tmp-git-暂存' "$lite\.git" -Force
Move-Item '<build-host>\_工作\_tmp-交付v094-暂存' "$lite\交付-v0.9.4" -Force
```

- 期望：恢复后按 `snapshots\v0.9.4-re1\snapshot.json` 核对 = **471 文件 / 7,545,125 B**；逐文件 sha256 与 `snapshots\v0.9.4-re1\manifest.sha256`（**48,649 B**）比对 **missing=0 / changed=0 / extra=0**（方案 A）；方案 B 放回交付目录后 `extra=5`（本版交付五件，属预期）。
- 注意：快照是 **re1 整树**（含 `MANIFEST.sha256` 的代码树版本，466 行）；恢复后 `git status` 会全量"已修改"（工作区与 HEAD 不一致属预期）——**恢复后不要直接 commit**，先 `git reset --hard lite-v0.9.4-re1` 对齐，或只在副本目录里用快照。
- **snap 也恢复得了**：把 `v0.9.4-snap` 换进命令即可（467 文件 / 7,271,120 B）；0.9.3 的目录快照也在（461/6,982,189）。

## 三、数据回滚口径（★ 本版重点）

### 3.1 一句话

**账库只追加、本版无数据迁移 → 代码回滚不用动账；本版新增的派生件（`.index/`、`MM月账.md`、`.tick-metrics` 新键）可留可删/可重建。**

### 3.2 逐对象口径

| 对象 | 回滚时怎么处理 | 为什么 |
|---|---|---|
| `ledger/YYYY-MM-DD.jsonl`（台账） | **不动** | append-only；按设计不允许"撤回一行"，只能补记/更正留痕 |
| `YYYY年MM月/…完整原文.md`、`原始事件.json`、附件 | **不动** | 本版不销毁原文（清理仍冻结），回滚不会产生"文件没了"的问题 |
| 周记账 `xlsx`（草稿/封板） | **不动** | 封板后字节不变（W2 之后连文件头都不再读）；未封板草稿由当前运行的代码按同一 v1.3 格式重写，**格式本版未变** |
| `ledger/.seal-journal.jsonl` | **不动** | 封板事实由摄入路径写；本版只改**读法**（W1 尾读缓存/W5 摘要），不改 journal 格式/写者 |
| `ledger/.state.json` | **不动**（注意新键） | 本版新增 `weeklyCatchup`；可能剪掉了已封板组的 `weeklyHashes`（W4）。旧代码忽略未知键；`weeklyHashes` 缺失只影响"重算判等"，不影响账——**但回滚前建议先跑一轮 tick 确认 `stat.weeklyDeferred=0`**（见 §3.4-1） |
| `ledger/.pending.jsonl`、`.run-report-*.json` | **不动** | 运行状态/报告，旧代码能读（本版未改 run-report 形状） |
| **`ledger/.tick-metrics.jsonl`（本版新键）** | **可留可删** | 运行度量旁证：本版加了 `weeklyDeferred/monthly/index` 三键；旧代码**不读它**，删掉不影响任何账务 |
| **`ledger/.index/`（本版新增索引目录）** | **可留可删、可重建** | 索引是**派生物**（C29 实测删了能逐字节重建）；旧代码不读；留着的副作用只是"目录比对会看到它"以及"内容会滞后"（§3.4-2） |
| **`YYYY年MM月/MM月账.md`（本版新增视图）** | **可留可删、可重建** | 由台账＋封板事实派生（指纹幂等）；旧代码不读；删掉后由"当前在跑的版本"在下次写月账时重建（若回滚到 0.9.3 则不再更新，内容停在回滚时刻） |
| `state.weeklyCatchup`（预算余量） | **不动** | 派生运行状态；旧代码不认这个键，不会"补做"余量组（§3.4-1） |
| 配置（`cordis.patch.yml`） | 用整树回滚（动作①）一并回退 | 本版 21 键与 0.9.3 **逐字节相同**（`scanBudgetMs` 仍是 30000），不存在混搭值问题 |
| 备份目录（`tools\backup.mjs` 的 `--out`） | **不动** | 备份是独立目录、自包含（`backup.json`＋`MANIFEST.sha256`＋`files/`）；回滚代码不影响已做备份；旧代码没有 backup 工具，但备份仍可用 re1 包的工具校验/恢复 |
| 公共库外锚 / 收据 | **不涉及** | 本版未启用、未写；收据能力按 S-1 已降级为日结摘要 |

### 3.3 回滚 = 换代码，四条硬理由

1. **台账行格式未变**：仍是 `{"v":3, code, ts, sid, turn, seq, status, turnState, src, doc, …}`；本版**没有动 `lib/ledger.js`**（KERNEL 六文件一字节未动）。
2. **配置 21 键未变且逐字节相同**：`cordis.patch.yml` 从 0.9.3 起未改（`scanBudgetMs: 30000`），回滚不会出现"代码与配置混搭"。
3. **数据总库布局未变**：`lib/layout.js` 本版未改；`.index/` 在 `ledger/` 下且以 `.` 开头，台账枚举/`readAll`/指纹都不把它当账行。
4. **本版不迁移旧库**：`legacy-marks` 冻结、`reconcile` 不读基线标记 → 本版没有"升级动作"要撤销；反过来，**本版也没有提供旧库升级路径**（见 03 §六）。

### 3.4 ★ 数据回滚的三个"必须知道"

1. **代码回滚 ≠ 数据补齐，也 ≠ 待办继续**：
   - 回滚到 `lite-v0.9.4-snap`：P3 功能代码都在，但 **tick 不再同步索引**（索引停在回滚时刻，要新索引只能手动 `node tools\cli.mjs index build`）；月账/备份仍可用但不再自动接 tick。
   - 回滚到 `lite-v0.9.3`：索引/月账/备份工具**从代码里消失**；`.index/`、`MM月账.md` 留在盘上但不再被维护。
   - **最要紧的一条**：若回滚时上一轮有"预算没跑完的周账组"（`stat.weeklyDeferred>0`，余量在 `state.weeklyCatchup`），回滚后旧代码**不认这个键、不会补做**——这些组要等下次真正被 touched 时才会重算。**建议回滚前在当前版本上再跑一轮 tick，确认 `weeklyDeferred=0`**（或接受"下次触及时补"）。
   - 已入账的 1,338 行不会因回滚消失；未入账的轮次旧代码也不会补。
2. **`.index/` 会让"目录全量比对/备份"出现差异**：旧代码不读它，但它**仍在**且不再增长；`tools\backup.mjs` 默认跳过索引与度量（`--include-index/--include-metrics` 才纳入）。审计口径：**索引可删可重建**（删掉=回到"无索引"状态，账一个字节不少），需要索引时用 re1 的工具重建。
3. **退到 v0.9.0 基座的"读语义差异"仍在**（沿 0.9.3 04 §3.4-3）：本版 `ledger/.seal-journal.jsonl` 按 S-1 只写"封板事实"（`prevSealSha256` 恒 `''`），0.9.0 基座代码读本版写过的库会把缺链行按"链断/坏行"处理 → 门可能降级。**默认回滚目标 `lite-v0.9.4-snap` / `lite-v0.9.3` / `lite-v0.9.2` 都是同一口径，没有这个问题；退基座只用于"整包回看/比对"。**

## 五、回滚演练（步骤 + 预期；实际结果由 lead 填）

> 演练纪律：在 `_工作\lite` 内做（动作③ 用副本目录）；演练前先 `git status` 确认没有未提交的已跟踪改动；演练只碰代码，不碰账库（`_工作\c01-lab` 只读跑判据/自检，不写）。

## 六、回滚不是"抹掉证据"

- **版本台账 append-only**：回滚后**不要删行**；要更正就追加更正行（台账红线）。
- **tag 保留**：`lite-v0.9.1` / `lite-v0.9.2` / `lite-v0.9.3` / `lite-v0.9.4-snap` / `lite-v0.9.4-re1` 与将来的 `lite-v0.9.4` 都是"这个版本存在过"的证据，**不要删**。
- **目录快照保留**：`_工作\snapshots\v0.9.4-re1`（471 文件 / 7,545,125 B）与 `v0.9.4-snap`（467 / 7,271,120）、`v0.9.3`（461 / 6,982,189）是逐字节复算的唯一依据，不要清。
- **证据保留**：`_工作\证据\` 下的 `094-criteria-*`（判据逐条 JSON 与 proof）、`094re1-wire-*.log`、`094-p3idx\`、`p3-设备自检-20261113\`、`094-p3-weekly-20261113.log`、`094-backup-20261113-191650.log`、`跑测试-094*-*.log`、`判据-094re1-*.log/json` 是 0.9.4 的现场证据；0.9.3 的 `093-*` 与 `判据-v0.9.1\`（28 份）也**不要删**（C01–C18/E3 的沿用依据）。
- **回滚不是修复**：回滚解决"本版代码有问题"，不解决"账库已经被写坏/没写全"；已入账的行不会因回滚消失，未入账的轮次旧代码也不会补；索引/月账是派生件，删了能重建、留着会滞后，都不是账务事实。
