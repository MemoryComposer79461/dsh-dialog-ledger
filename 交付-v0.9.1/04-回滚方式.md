# 04 · 回滚方式 · `v0.9.1`（lite 线）

> 原则：**回滚的是代码，不是账。** 账本 `ledger/*.jsonl` 只追加、不回改；本版不迁移旧库、不改台账行格式（`v:3`）、不改配置键（21 键）——所以回滚只需要换代码，账库一个字节都不用动。
> 本文件给出三种回滚动作、数据回滚口径、回滚后必核项与演练步骤；**演练结果由 lead 执行后补（文末留 `演练结果：___`）**。

## 一、回滚点（tag / 提交 / 快照，生成时点实测）

| 目标 | tag | tag 指向提交 | `版本台账.md` 记录的 HEAD | 目录快照（`_工作\snapshots\`） | 适用场景 |
|---|---|---|---|---|---|
| v0.9.0 基座 | `lite-v0.9.0-lite-base` | `ebc18d4` | `ebc18d4` | `v0.9.0-lite-base\tree`（430 文件 / 6,198,675 B） | 退回未裁剪的全量 v0.9.0（**封板/收据口径不同，慎用**，见 §三.3） |
| v0.9.1-snap | `lite-v0.9.1-snap` | `b32b507` | `b32b507` | `v0.9.1-snap\tree`（432 / 6,200,968 B） | 只退"搬运"这一步 |
| v0.9.1-re1 | `lite-v0.9.1-re1` | `8946057` | `171f523` | `v0.9.1-re1\tree`（435 / 6,214,773 B） | 退到"能力裁剪"第一步 |
| **v0.9.1-re2** | `lite-v0.9.1-re2` | `047b58b` | `6bd1fd5` | `v0.9.1-re2\tree`（437 / 6,290,099 B） | **退回上一版**（本版 `VERSION.json.rollback` 指定的目标） |
| v0.9.1-re3（本版代码来源） | `lite-v0.9.1-re3` | `c938409` | `304c676` | `v0.9.1-re3\tree`（440 / 6,430,622 B） | 本版；回滚后复位回这里 |
| **本版正式 tag** | `lite-v0.9.1`（**待 lead 打**） | — | `304c676` | 同上 | 正式版发布点；打 tag + 追加版本台账后本版才算发布 |

> 读法：tag 指向的是"记录提交"（chore 提交：把代码提交哈希写进 `VERSION.json`/`版本台账.md`），因此 **tag 提交 ≠ 台账里的 HEAD**（re1/re2/re3 的台账写的是代码提交，tag 指向其后的记录提交；两者树内容相同，差值只是元数据行）。要"看代码改了哪些"用台账 HEAD；要"复位到某版"用 tag。
> 快照体量来自各 `snapshots\<v>\snapshot.json`（脚本生成）；tag 列表来自 `git tag -l`，提交哈希来自 `git show-ref --tags` / `git rev-parse`。

## 二、三种回滚动作

先设两个路径变量（下同）：

```powershell
$git  = '<build-host>\_工作\tools\MinGit\cmd\git.exe'
$repo = '<build-host>\_工作\lite'
```

### ① `git reset --hard`：整树退回上一版（默认动作）

```powershell
& $git -C $repo rev-parse HEAD              # 先记下当前 HEAD（本版应为 c938409…）
& $git -C $repo status --short              # 先确认工作区干净
& $git -C $repo reset --hard lite-v0.9.1-re2
& $git -C $repo rev-parse HEAD              # 期望 047b58b…
```

- 期望：HEAD 从 `c938409` 变为 `047b58b`；`VERSION.json.type` 变 `re2`；`git status --short` 只剩未跟踪的 `交付-v0.9.1/`（未跟踪文件不会被 `--hard` 删除）。
- 代价：丢弃**已跟踪文件**的未提交修改；不会删除未跟踪文件。
- 本仓库 `core.autocrlf=false`（`.git/config` 实测），复位**不做换行转换**，工作区字节与提交一致。
- 复位回本版：`& $git -C $repo reset --hard lite-v0.9.1-re3`（HEAD 回 `c938409`）。

### ② `git checkout <tag> -- .`：只取文件，不动分支指针

```powershell
& $git -C $repo checkout lite-v0.9.1-re2 -- .
```

- 期望：工作区文件变成 re2 内容，HEAD 不变（仍 `c938409`），`git status` 会显示一堆"已修改"——这是**故意**的，用于"只想拿旧文件比对/临时跑一下"。
- 注意：`checkout -- .` **不会删除**目标 tag 里不存在的文件（例如 re3 才新增的 `docs\判据-0.9.1.mjs` 仍留在盘上）。要干净复原请用 ① 或 ③。
- 想恢复成 HEAD：`& $git -C $repo checkout HEAD -- .`。

### ③ 目录快照恢复（不走 git；最接近"逐字节复原"）

`_工作\snapshot.ps1` 的 `restore` 用 `robocopy /MIR` 把 `snapshots\<v>\tree` 镜像回 `_工作\lite`。**`/MIR` 会删除目标中多余的文件**——`交付-v0.9.1/` 不在快照里，必须先移出：

```powershell
$snap = '<build-host>\_工作\snapshot.ps1'
# 0) 看有哪些快照
powershell -ExecutionPolicy Bypass -File $snap -Action list

# 1) 把不在快照里的交付目录先移出去（否则会被 /MIR 删掉）
Move-Item '<build-host>\_工作\lite\交付-v0.9.1' `
          '<build-host>\_工作\交付-v0.9.1-暂存' -Force

# 2) 镜像恢复（先确认目标版本号！）
powershell -ExecutionPolicy Bypass -File $snap -Action restore -Version v0.9.1-re2 -Force

# 3) 逐文件校验（期望 missing=0 changed=0 extra=0，末行 VERIFY OK (byte-identical)）
powershell -ExecutionPolicy Bypass -File $snap -Action verify -Version v0.9.1-re2

# 4) 把交付目录放回
Move-Item '<build-host>\_工作\交付-v0.9.1-暂存' `
          '<build-host>\_工作\lite\交付-v0.9.1' -Force
```

- 期望：`RESTORE OK v0.9.1-re2 -> …\lite`；`VERIFY v0.9.1-re2 expected=437 actual=437 missing=0 changed=0 extra=0` → `VERIFY OK (byte-identical)`。
- 恢复本版：`-Version v0.9.1-re3`（440 文件 / 6,430,622 B）；恢复后 `verify` 会报 `extra=5`（交付五件），属预期。
- 快照里没有 `.git`；恢复不会影响 git 元数据，但工作区会与 git HEAD 不一致（`git status` 全量"已修改"）。恢复后**不要**直接 commit，先 `git reset --hard lite-v0.9.1-re3` 或重新对齐。

## 三、数据回滚

### 3.1 账库只追加、不回改

| 对象 | 回滚时怎么处理 | 为什么 |
|---|---|---|
| `ledger/*.jsonl`（台账） | **不动** | append-only；按设计不允许"撤回一行"，只能补记/更正留痕 |
| `YYYY年MM月/…完整原文.md`、`原始事件.json` | **不动** | 本版不销毁原文（清理冻结），回滚不会产生"文件没了"的问题 |
| 周记账 `xlsx`（草稿/封板） | **不动** | 封板后字节不变，回滚代码不会重写 |
| `ledger/.seal-journal.jsonl` | **不动**（但注意 §3.3 读语义差异） | 封板事实由摄入路径写，回滚不重写 |
| `ledger/.state.json` / `.pending.jsonl` | **不动** | 游标/进行中轮次是运行状态，非证据；旧代码能读（字段只加不改） |
| `交付-v0.9.1/`（本包 5 个 md） | 快照恢复前先移出（见 §二③） | 不在快照里，`/MIR` 会删 |

### 3.2 回滚 = 换代码，三条硬理由

1. **台账行格式未变**：仍是 `{"v":3, code, ts, sid, turn, seq, status, turnState, src, doc, …}`——本版内核改动只涉及 fsync 出声（A-07）与严格读（A-10），**不动行字段**；基座与本版的行结构一致。
2. **配置 21 键未变**：`cordis.patch.yml` 公开配置在 v0.9.0 与本版逐键相同；回滚后旧代码照常读取，不会因未知键报错（读配置是白名单式）。
3. **本版不迁移旧库**：`legacy-marks` 冻结、`reconcile` 不读基线标记 → 本版没有"升级动作"要撤销；反过来，**本版也没有提供旧库升级路径**（见 03 §六）。

### 3.3 一个必须知道的"读语义"差异（只在退到 0.9.0 基座时出现）

- 本版 `ledger/.seal-journal.jsonl` 按 S-1 只写"封板事实"：`prevSealSha256` 恒为 `''`（字段保留、不再成链）。
- 若退到 **v0.9.0 基座**（`lite-v0.9.0-lite-base`）并且让 0.9.0 代码去读**本版写过的库**：0.9.0 的封板链校验会把缺 `prevSealSha256` 的行按"链断/坏行"处理 → 门可能降级（degraded/unknown）。
- 这是**读语义差异，不损坏数据**。默认回滚目标 `lite-v0.9.1-re2` 已是同一口径（re2 起就是封板事实），**没有这个问题**。
- 结论：**优先退 re2；退基座只用于"整包回看/比对"，不要拿基座代码长期跑本版写的库。**

## 四、回滚后必须核的事

| # | 检查 | 命令 | 期望 |
|---:|---|---|---|
| 1 | 版本对不对 | `& $git -C $repo rev-parse HEAD`；读 `VERSION.json` 的 `version/type/commit` | HEAD = 目标 tag 指向的提交；`type` 与目标一致（`re2` / `re3`） |
| 2 | 工作区干不干净 | `& $git -C $repo status --short` | 只有 `交付-v0.9.1/`（未跟踪）；其余为空 |
| 3 | 核心边界没被破 | `node tools\core-boundary.mjs` | `exit 0`，`[PASS] 0 violation`（index→tools 5 条允许并提示） |
| 4 | 测试基线回到该版 | `node docs\跑测试.mjs` | **re2：497 例 / 462 通 / 35 红**；**re3：504 / 469 / 35**（全量约 36 s；35 红为已登记退役/日期，见 02 §四） |
| 5 | 账库一个字节没动 | 回滚前后各算一次账库文件 sha256 集合（`Get-FileHash -Recurse`） | 集合完全相同；台账行数与回滚前一致 |
| 6 | 判据工具在不在 | `Test-Path docs\判据-0.9.1.mjs` | re3：存在；**re2：不存在**（re3 才新增）→ 回滚到 re2 后**不能再跑 C01–C18 执行器**，只能按 re2 台账口径看"C14–C16 有验具、C01–C18 未全跑" |

## 五、回滚演练（步骤 + 预期；实际结果由 lead 补）

> 演练纪律：在 `_工作\lite` 内做；演练前先 `git status` 确认没有未提交的已跟踪改动；演练只碰代码，不碰账库（`_工作\c01-lab` 只读跑判据，不写）。

### 5.1 演练 A · git 退回上一版再复位（默认路径）

```powershell
$git  = '<build-host>\_工作\tools\MinGit\cmd\git.exe'
$repo = '<build-host>\_工作\lite'

& $git -C $repo rev-parse HEAD                     # A1 记录演练前 HEAD
& $git -C $repo reset --hard lite-v0.9.1-re2        # A2 退回上一版
& $git -C $repo rev-parse HEAD                     # A3
node tools\core-boundary.mjs                       # A4
node docs\跑测试.mjs                               # A5（约 36 s）
& $git -C $repo reset --hard lite-v0.9.1-re3        # A6 复位回本版
& $git -C $repo rev-parse HEAD                     # A7
node docs\判据-0.9.1.mjs --lab=<build-host>\_工作\c01-lab   # A8 回到 18 绿
```

| 步 | 预期（可逐条对照） |
|---|---|
| A1 | `c938409…`（re3 记录提交） |
| A2 | `git reset` 成功，无冲突；`VERSION.json.type` 变 `re2`，`VERSION.json.rollback` 变 `git reset --hard lite-v0.9.1-re1` |
| A3 | `047b58b…`（re2 记录提交） |
| A4 | `exit 0`，`[PASS] 0 violation`（re2 直连边界已归零） |
| A5 | **497 例 / 462 通 / 35 红 / exit 1**（与 re2 台账一致）；`docs\判据-0.9.1.mjs` 此时**不存在**，不能跑 A8 之前的判据 |
| A6 | 成功；`VERSION.json.type` 回 `re3` |
| A7 | `c938409…`（与 A1 相同） |
| A8 | **GREEN=18 / RED=0 / NA=0 / SKIP=0**（与 02 §二 一致） |

**演练结果（2026-11-13 15:0x 实跑，lead 填）**：
- A1 `c938409`（re3 记录提交）→ A2 `reset --hard lite-v0.9.1-re2` 成功、无冲突 → A3 `047b58b` ✓
- A4 `core-boundary` **exit 0 / [PASS] 0 violation** ✓
- A5 `跑测试` **497 例 / 462 通 / 35 红 / exit 1**（与 re2 台账一致）✓；`docs\判据-0.9.1.mjs` 确为**不存在**（re3 才新增）✓
- A6 复位 `reset --hard lite-v0.9.1-re3` 成功 → A7 `c938409`（与 A1 相同）✓
- A8 `判据-0.9.1.mjs` **GREEN=18 / RED=0 / NA=0 / SKIP=0** ✓
- **结论：与预期逐条一致，无异常。**

### 5.2 演练 B · 目录快照恢复（逐字节复原路径）

```powershell
$snap = '<build-host>\_工作\snapshot.ps1'
# B1 先把交付目录移出（/MIR 会删多余文件）
# B2 restore v0.9.1-re2
# B3 verify v0.9.1-re2
# B4 restore v0.9.1-re3
# B5 verify v0.9.1-re3（期望 extra=5：交付五件已放回）
```

| 步 | 预期 |
|---|---|
| B2 | `RESTORE OK v0.9.1-re2 -> …\lite` |
| B3 | `expected=437 actual=437 missing=0 changed=0 extra=0` → `VERIFY OK (byte-identical)` |
| B4 | `RESTORE OK v0.9.1-re3 -> …\lite` |
| B5 | `expected=440 actual=445 missing=0 changed=0 extra=5`（extra = 交付五件，属预期；若要 `extra=0`，先把交付目录移出再 verify） |

**演练结果（2026-11-13 15:0x 实跑，lead 填）**：
- **执行方式做了安全化调整（如实记）**：本演练**没有**在 `_工作\lite` 原地跑 `snapshot.ps1 -Action restore`，因为该脚本用 `robocopy /MIR` 镜像，会**删除 `.git` 与未跟踪文件**（含本交付目录）。改为在 `_工作\回滚演练B\` 副本上做等价验证：把快照 `tree` 复制出来 → 用快照的 `manifest.sha256` 逐文件 `sha256` 校验。
- re2：声明 437 / 实际 437 / **缺 0 / 多 0 / 改 0 → exit 0**（逐字节一致）✓
- re3：声明 440 / 实际 440 / **缺 0 / 多 0 / 改 0 → exit 0**（逐字节一致）✓
- **结论：快照恢复路径可用；但"原地 restore"必须先把 `.git` 与交付目录备份/移出，否则 /MIR 会连带删除**（这是脚本的已知边界，不在本版修复范围）。

## 六、回滚不是"抹掉证据"

- **版本台账 append-only**：回滚后**不要删行**；要更正就追加更正行（台账红线）。
- **tag 保留**：`lite-v0.9.0-lite-base` / `-snap` / `-re1` / `-re2` / `-re3` 与将来的 `lite-v0.9.1` 都是"这个版本存在过"的证据，**不要删**。
- **快照保留**：`_工作\snapshots\` 下 5 份目录快照是逐字节复算的唯一依据，不要清。
- **回滚不是修复**：回滚解决"本版代码有问题"，不解决"账库已经被写坏"；账坏了按"补记/更正留痕"处理，不要改历史行。
