# 04 · 回滚方式 · `v0.9.2`（lite 线）

> 原则：**回滚的是代码，不是账。** 账本 `ledger/*.jsonl` 只追加、不回改；本版不迁移旧库、不改台账行格式（`v:3`）、不改配置键（21 键）、不改数据总库布局——所以回滚只需要换代码，账库一个字节都不用动。
> 本文件给出三种回滚动作、数据回滚口径、回滚后必核项与演练步骤；**演练结果已由 lead 实跑并填在文末（§五 之后）**。
> 依据：`VERSION.json`（`baselineTag=lite-v0.9.2-snap`、`rollback=git reset --hard lite-v0.9.2-snap`）；tag/提交/快照数字均为生成时点现场实测。

## 一、回滚点（tag / 提交 / 快照，生成时点实测）

| 目标 | tag | tag 指向提交 | `VERSION.json` / 台账记录 | 目录快照（`_工作\snapshots\`） | 适用场景 |
|---|---|---|---|---|---|
| v0.9.1 正式版 | `lite-v0.9.1` | `84fce51` | 台账第 5 行（构建自 `c938409`） | `v0.9.1\tree`（**446 文件 / 6,546,377 B**，含 `MANIFEST` 与 `交付-v0.9.1/`） | 退回 0.9.1 正式版（**本版只改 tools/index，账库口径同 0.9.1，可安全退**） |
| v0.9.2-snap | `lite-v0.9.2-snap` | `c045925` | 代码提交 `7f2027a`；台账第 6 行 | `v0.9.2-snap\tree`（448 / 6,606,478 B） | **退回本次开工前**（本版 `VERSION.json.rollback` 指定的目标） |
| v0.9.2-re1（本版构建依据） | `lite-v0.9.2-re1` | `8b71085` | 代码提交 `6f8d0c4`；台账第 7 行 | `v0.9.2-re1\tree`（**449 / 6,653,583 B**） | 本版；回滚后复位回这里 |
| **本版正式 tag** | `lite-v0.9.2`（**待 lead 打**） | — | `VERSION.json.version=0.9.2`；`type=re1` 升正式 | 同上 | 正式版发布点；打 tag + 追加版本台账后本版才算发布 |

> 读法：tag 指向的是"记录提交"（chore：把代码提交哈希写进 `VERSION.json`/`版本台账.md` 的那次），因此 **tag 提交 ≠ 代码提交**（`lite-v0.9.2-snap` 指向 `c045925`，其代码提交是 `7f2027a`；`lite-v0.9.2-re1` 指向 `8b71085`，其代码提交是 `6f8d0c4`）。两者树内容只差元数据行。要"看代码"用代码提交；要"复位到某版"用 tag。
> 快照体量来自各 `snapshots\<v>\snapshot.json`；tag→提交来自 `git rev-parse <tag>^{commit}`；HEAD = `8b71085`（`8b71085e7ca87a41a1dab2ae7521171d8149a5b5`），`git status --short` 为空。

## 二、三种回滚动作

先设两个路径变量（下同）：

```powershell
$git  = '<build-host>\_工作\tools\MinGit\cmd\git.exe'
$repo = '<build-host>\_工作\lite'
```

### ① `git reset --hard`：整树退回上一版（默认动作）

```powershell
& $git -C $repo rev-parse HEAD              # 先记下当前 HEAD（本版应为 8b71085…）
& $git -C $repo status --short              # 先确认工作区干净
& $git -C $repo reset --hard lite-v0.9.2-snap   # 退回开工前（本版 VERSION.json.rollback）
& $git -C $repo rev-parse HEAD              # 期望 c045925…
```

- 期望：HEAD 从 `8b71085` 变为 `c045925`；`VERSION.json.type` 变 `snap`、`VERSION.json.rollback` 变回指向 0.9.1；`git status --short` 只剩未跟踪的 `交付-v0.9.2/`（未跟踪文件不会被 `--hard` 删除）。
- 代价：丢弃**已跟踪文件**的未提交修改；不会删除未跟踪文件（`交付-v0.9.1/`、`交付-v0.9.2/` 是已跟踪目录，`--hard` 会把它们恢复成目标版本中的样子——`交付-v0.9.1/` 在 `lite-v0.9.2-snap` 里存在，`交付-v0.9.2/` 不在任何旧 tag 里，属未跟踪，保留）。
- 本仓库 `core.autocrlf=false`（0.9.1 实测；本版未改），复位**不做换行转换**，工作区字节与提交一致。
- 退回 0.9.1 正式版：`& $git -C $repo reset --hard lite-v0.9.1`（HEAD 变 `84fce51`；测试基线回到 **504 / 469 / 35**、内核检查回到"对 0.5.0 基线红、恰 2 changed"）。
- 复位回本版：`& $git -C $repo reset --hard lite-v0.9.2-re1`（HEAD 回 `8b71085`）。

### ② `git checkout <tag> -- .`：只取文件，不动分支指针

```powershell
& $git -C $repo checkout lite-v0.9.2-snap -- .
# 或只退单个文件（例：把 toolface 退回 9 个工具）
& $git -C $repo checkout lite-v0.9.2-snap -- tools/toolface.js tools/toolcards.js
```

- 期望：工作区文件变成目标 tag 内容，HEAD 不变，`git status` 显示一堆"已修改"——这是**故意**的，用于"只拿旧文件比对/临时跑一下/只退一个模块"。
- 注意：`checkout -- .` **不会删除**目标 tag 里不存在的文件（例如本版新增的 `tools\doctor.mjs`、`docs\判据-0.9.2-doctor.mjs`、`docs\内核基线\内核基线-v1.0-lite.sha256` 会留在盘上）。要干净复原请用 ① 或 ③。
- 想恢复成 HEAD：`& $git -C $repo checkout HEAD -- .`。

### ③ 目录快照恢复（不走 git；最接近"逐字节复原"）

`_工作\snapshot.ps1` 的 `restore` 用 `robocopy /MIR` 把 `snapshots\<v>\tree` 镜像回 `_工作\lite`。**`/MIR` 会删除目标中多余的文件**——本版交付目录 `交付-v0.9.2/` 不在任何快照里，**必须先移出**（`交付-v0.9.1/` 在 `snapshots\v0.9.1` 及之后的快照里都有，但为了统一，建议也一并移出再放回）：

```powershell
$snap = '<build-host>\_工作\snapshot.ps1'
# 0) 看有哪些快照
powershell -ExecutionPolicy Bypass -File $snap -Action list

# 1) 把不在快照里的交付目录先移出去（否则会被 /MIR 删掉）
Move-Item '<build-host>\_工作\lite\交付-v0.9.2' `
          '<build-host>\_工作\交付-v0.9.2-暂存' -Force

# 2) 镜像恢复（先确认目标版本号！）
powershell -ExecutionPolicy Bypass -File $snap -Action restore -Version v0.9.2-snap -Force

# 3) 逐文件校验（期望 missing=0 changed=0 extra=0，末行 VERIFY OK (byte-identical)）
powershell -ExecutionPolicy Bypass -File $snap -Action verify -Version v0.9.2-snap

# 4) 把交付目录放回
Move-Item '<build-host>\_工作\交付-v0.9.2-暂存' `
          '<build-host>\_工作\lite\交付-v0.9.2' -Force
```

- 期望：`RESTORE OK v0.9.2-snap -> …\lite`；`VERIFY v0.9.2-snap expected=448 actual=448 missing=0 changed=0 extra=0` → `VERIFY OK (byte-identical)`。
- 恢复本版：`-Version v0.9.2-re1`（449 文件 / 6,653,583 B）；恢复后 `verify` 会报 `extra=5`（交付五件，属预期；若要 `extra=0` 先把交付目录移出再 verify）。
- 快照里没有 `.git`；恢复不会影响 git 元数据，但工作区会与 git HEAD 不一致（`git status` 全量"已修改"）。恢复后**不要**直接 commit，先 `git reset --hard lite-v0.9.2-re1` 或重新对齐。

## 三、数据回滚

### 3.1 账库只追加、不回改

| 对象 | 回滚时怎么处理 | 为什么 |
|---|---|---|
| `ledger/*.jsonl`（台账） | **不动** | append-only；按设计不允许"撤回一行"，只能补记/更正留痕 |
| `YYYY年MM月/…完整原文.md`、`原始事件.json` | **不动** | 本版不销毁原文（清理仍冻结），回滚不会产生"文件没了"的问题 |
| 周记账 `xlsx`（草稿/封板） | **不动** | 封板后字节不变，回滚代码不会重写 |
| `ledger/.seal-journal.jsonl` | **不动** | 封板事实由摄入路径写，回滚不重写（本版仍按 S-1 只写"封板事实"，与 0.9.1 同口径） |
| `ledger/.state.json` / `.pending.jsonl` | **不动** | 游标/进行中轮次是运行状态，非证据；旧代码能读（字段只加不改） |
| `ledger/.run-report-YYYYMMDD.json` | **不动** | 本版报告不再写 `backfill` 段；0.9.1 读侧不要求该段（`lib/report.js` 只在传对象时落键），旧代码读新报告不报错 |
| `<root>/报告/doctor-YYYYMMDD-NN.json` | 可留可删（**可弃产物**） | 只有跑过 doctor 才有；留着不参与记账。注意 `报告/` 是**新的一级目录**，`lib/layout.js` 会把它记进 `unknown[]`（0.9.1/0.9.2 都一样，`layout.js` 本版未改）——回滚前若跑过 doctor，这是预期现象，不是布局被破坏 |
| `交付-v0.9.2/`（本包 5 个 md） | 快照恢复前先移出（见 §二③） | 不在快照里，`/MIR` 会删 |

### 3.2 回滚 = 换代码，四条硬理由

1. **台账行格式未变**：仍是 `{"v":3, code, ts, sid, turn, seq, status, turnState, src, doc, …}`——本版**没有动 `lib/`**（21/21 逐字节同 0.9.1），行结构自然一致。
2. **配置 21 键未变**：`cordis.patch.yml` 公开配置在 0.9.1 与本版逐键同值；回滚后旧代码照常读取（含 `cleanupToolEnabled`/`cleanupAllowPhysicalDelete` 两键，本版保留不删）。
3. **数据总库布局未变**：`lib/layout.js` 本版未改。
4. **本版不迁移旧库**：`legacy-marks` 冻结、`reconcile` 不读基线标记 → 本版没有"升级动作"要撤销；反过来，**本版也没有提供旧库升级路径**（见 03 §四）。

### 3.3 ★ 数据回滚的两个"必须知道"（本版新情况）

1. **代码回滚 ≠ 数据补齐**：E3 实测本版在 38.82 MB 大语料上只入账 48/1,338 轮、游标停在 `offset=187`/`partialCommit=true`、之后每轮重读约 16 MB 且 0 写入（`_工作\计划\E2-E3-实测-20261113.md`）。**回滚到 0.9.1 不会把没入账的 1,290 轮补回来**——旧代码同样按 `.state.json` 游标继续，缺陷是否同样存在本版未单独复测（05 #3）。正确做法：等 0.9.3 修好后用修好的版本重跑 ingest（从该游标重读会重扫大文件，属修点的一部分）。
2. **退到 v0.9.0 基座的"读语义差异"仍在**（沿 0.9.1 04 §3.3）：本版 `ledger/.seal-journal.jsonl` 按 S-1 只写"封板事实"（`prevSealSha256` 恒 `''`），0.9.0 基座代码读本版写过的库会把缺链行按"链断/坏行"处理 → 门可能降级。**默认回滚目标 `lite-v0.9.2-snap`/`lite-v0.9.1` 都是同一口径，没有这个问题；退基座只用于"整包回看/比对"。**

## 四、回滚后必须核的事

| # | 检查 | 命令 | 期望 |
|---:|---|---|---|
| 1 | 版本对不对 | `& $git -C $repo rev-parse HEAD`；读 `VERSION.json` 的 `version/type/commit` | HEAD = 目标 tag 指向的提交；`type` 与目标一致（`snap` / `re1` / 0.9.1 的 `正式`） |
| 2 | 工作区干不干净 | `& $git -C $repo status --short` | 只有 `?? 交付-v0.9.2/`（未跟踪）；其余为空 |
| 3 | 核心边界没被破 | `node tools\core-boundary.mjs` | **re1：exit 0，`[PASS] 0 violation`，index→tools 3 条**（shadow/panelapi + 白名单 toolface）；**0.9.1：exit 0，0 violation，index→tools 5 条**；**0.9.2-snap：同 re1**（本版边界改动在 snap 已完成） |
| 4 | 内核基线对不对 | `node docs\验收-v0.5\工具-内核边界检查.mjs` | **re1 / snap：`[PASS] exit 0`**（默认选 v1.0-lite）；**0.9.1：exit 1，`ledger.js`/`sealjournal.js` 2 个 changed**（0.9.1 无 v1.0-lite 基线，工具还是 v1.0） |
| 5 | 测试基线回到该版 | `node docs\跑测试.mjs` | **re1：504 / 460 / 44**；**snap：504 / 460 / 44**（本版产品代码在 snap 后未变）；**0.9.1：504 / 469 / 35**（全量约 38 s；44/35 红均为已登记退役/日期，见 02 §四） |
| 6 | 判据工具在不在 | `Test-Path docs\判据-0.9.1.mjs`；`Test-Path docs\判据-0.9.2-doctor.mjs` | **re1：两个都在**；**snap：判据-0.9.2-doctor 不存在**（re1 才新增）；**0.9.1：判据-0.9.1 在、doctor 门脚本不存在** |
| 7 | 账库一个字节没动 | 回滚前后各算一次账库文件 sha256 集合（`Get-FileHash -Recurse`） | 集合完全相同；台账行数与回滚前一致（E3 场景下**行数不会因回滚变多**，见 §3.3①） |

> 内存护栏：`node docs\跑测试.mjs` 在可用内存 <900 MB 时**拒绝启动（exit 3）**，不是测试失败；回滚后若机器忙，先释放内存再跑（本版 15:34 判据首跑就踩过，见 02 §一）。

## 五、回滚演练（步骤 + 预期；实际结果由 lead 补）

> 演练纪律：在 `_工作\lite` 内做；演练前先 `git status` 确认没有未提交的已跟踪改动；演练只碰代码，不碰账库（`_工作\c01-lab` 只读跑判据，不写）。

### 5.1 演练 A · git 退回开工前再复位（默认路径）

```powershell
$git  = '<build-host>\_工作\tools\MinGit\cmd\git.exe'
$repo = '<build-host>\_工作\lite'

& $git -C $repo rev-parse HEAD                     # A1 记录演练前 HEAD
& $git -C $repo reset --hard lite-v0.9.2-snap        # A2 退回本版开工前
& $git -C $repo rev-parse HEAD                     # A3
```

### 5.3 演练 C · 只取文件（`checkout <tag> -- .`）

```powershell

& $git -C $repo status --short | Measure-Object -Line   # C2 大量 M
```

| 步 | 预期 |
|---|---|
| C1 | 成功；HEAD 不变（`8b71085`） |
| C2 | 出现大量 ` M`（工作区被 snap 内容覆盖），但 `tools\doctor.mjs`、`docs\判据-0.9.2-doctor.mjs`、`docs\内核基线\内核基线-v1.0-lite.sha256` **仍在**（`checkout -- .` 不删多余文件） |

**演练结果（2026-11-13 16:0x 实跑，lead 填）**： - **A（git 往返）**：A1 `8b71085` → A2/A3 退回 `lite-v0.9.2-snap`=`c045925`（`core-boundary` exit 0；内核检查 PASS v1.0-lite）→ A6/A7 复位 `8b71085`；**与预期一致**。A5（全量测试）本次因机器可用内存 0.84 GB < 护栏 0.88 GB 被拒绝启动（exit 3，非测试失败；本版首跑也踩过一次，见 02 §一），快照/re1 两树代码相同（re1 仅多一个验收脚本），测试结果以 02 §四 的 **504/460/44** 为准。 - **B（快照恢复）**：安全化变体（副本验证，避免 `/MIR` 删除 `.git` 与交付目录）：快照清单含"MANIFEST 自指行"已过滤；`v0.9.2-snap` **447/447**、`v0.9.2-re1` **448/448** 逐字节一致、`缺0/多0/改0` exit 0。**结论：恢复路径可用；原地 restore 前必须先备份/移出 `.git` 与交付目录。** - **C（checkout 文件）**：C1 成功、HEAD 不变；C2 出现 4 项 ` M`，`tools\doctor.mjs`、`docs\判据-0.9.2-doctor.mjs`、`docs\内核基线\内核基线-v1.0-lite.sha256` 仍在；C3 还原后除 `交付-v0.9.2/`（未跟踪）外 **0 项变更**；**与预期一致**。

## 六、回滚不是"抹掉证据"

- **版本台账 append-only**：回滚后**不要删行**；要更正就追加更正行（台账红线）。
- **tag 保留**：`lite-v0.9.1` / `-v0.9.2-snap` / `-v0.9.2-re1` 与将来的 `lite-v0.9.2` 都是"这个版本存在过"的证据，**不要删**。
- **快照保留**：`_工作\snapshots\` 下 8 份目录快照（含 `v0.9.2-snap`、`v0.9.2-re1`）是逐字节复算的唯一依据，不要清。
- **回滚不是修复**：回滚解决"本版代码有问题"，不解决"账库已经被写坏/没写全"；E3 的 48/1,338 只能靠 0.9.3 修复后重跑 ingest，不能靠回滚补齐。
